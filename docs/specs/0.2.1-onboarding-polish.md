# Spec: Onboarding and polish (0.2.1)

Status: design spec, ready to build. It covers the first run, the orchestrator's first words, the optional tmux home for the orchestrator, and a polish pass over everything `cadrei` prints. It changes no file formats. What it adds on the machine (uninstall and guide.md, 9.1, follow this list):

- in `~/.cadrei/config`: only things it can rebuild or ask again (7.9.2): the state keys `identity_warned` (3.6), `hook_offer` (5.5) and `first_task_pending` (5.1), and the marker `team-line-hint` (5.8.6);
- in each crew: the `ORCHESTRATOR` key in `cadrei.conf` (4.6), and the git-ignored folder `.claude/local/` with `places.json`, `state.json` and an optional `cadrei.conf` override (7.9.1);
- in each crew's `.claude/build/`: `orchestrator-settings.json` (5.1), the `state/` folder with member states and safeguard caches (7.3, 7.7);
- in `~/.claude.json`: a trust mark for a crew folder the first run or `cadrei new` creates (T9);
- in `~/.claude/settings.json`: no new entry (the every-chat hook stays one `SessionStart` entry), but its command takes the 5.1 form;
- in `cadrei ls --json`: new fields (7.3, 7.7, 7.11, 7.13), with `version` still 1, now a documented public interface, plus the `--watch` stream (7.13);
- with `cadrei uninstall --archive`: `~/.cadrei-archive/` (7.8).

How to read it: every block marked `text` is exact copy. Words in `<angle brackets>` are filled in at run time. Styling (color, bold, dim) is described in section 2 and is not shown inside the blocks. Unless a block says otherwise, it shows the styled mode with a terminal 80 columns or wider.

## 1. Decisions

Approved by the user:

1. The orchestrator speaks first on every run. On the first run it sends a full greeting with three starter tasks. On later runs it sends a short greeting of up to three lines that names itself and the crew, shows the team line, and the one thing that matters most (5.3). It does this every time cadrei opens it, a resumed chat included.
2. The orchestrator runs the read-only commands `cadrei ls`, `cadrei ls --json` and `cadrei allow list` without asking. Members' grants don't change.
3. The "every Claude Code chat is the orchestrator" hook is no longer offered on the first run. The orchestrator offers it once, after the first task works.
4. The first crew is named `main` automatically. There's no name question.
5. No git identity: one warning line, once.
6. Enter means yes to the whole plan, including adding the current folder as the first project. (Refined for safety, see 3.1: Enter adds the folder only when the repo has no Claude Code settings of its own. Otherwise its line is left out, and the user adds it with `a`.)
7. Color and the marks ✓ ! ✗, with a plain-text fallback for NO_COLOR, pipes and dumb terminals.
8. The first suggested task is a read-only review of the repo.
9. Restore from GitHub is the `r` key during setup.
10. The setup plan offers tmux for the orchestrator, recommends it with a reason, and Enter accepts it. One key picks the plain terminal instead. The choice is saved, and the user can change it later by asking. People who pick tmux get a gentle setup: mouse on, key hints in the status bar, the keys in the plan (they replaced the 4-line tutorial, 3.1), reuse of a tmux they're already in, and reattaching on the next `cadrei`.
11. Cadrei notices when Claude's safeguards stopped a member's reply (7.7): `cadrei up` warns after it starts or resumes such a member, `cadrei ls` shows a "stopped by safeguards" state, and the orchestrator hears about it in its snapshot and tells the user right away.
12. While any member runs, the orchestrator ends every reply with one short team status line, members waiting on the user or stopped by safeguards first (5.8). The data comes fresh on every message from a `UserPromptSubmit` hook in the orchestrator-only settings, with no tool call. There's no live panel or separate live view: `cadrei ls` stays a one-time screen.
13. A full uninstall that archives instead of deleting, and a restore that brings everything back (7.8). `cadrei uninstall --archive` removes the system parts as today, and also moves every crew and `~/.cadrei/config` into `~/.cadrei-archive/<date-time>/`, so a reinstall is a true first run. The first run offers an archive with `o`, and `cadrei restore` brings one back at the same paths. Projects, trust marks, Claude Code chats and the user's own Claude Code settings are never touched.
14. The engine and the user's crews don't depend on each other, as in Docker: the program, `~/.cadrei/framework` and `~/.cadrei/config` are the engine, and a crew folder is the volume (7.9). Everything about a crew lives in it, so `~/.cadrei/config` and `~/.cadrei/framework` can be deleted at any time and the next `cadrei` rebuilds them. After a reinstall, the first run finds the crews already in `~/.cadrei` and plugs them back in with one yes (3.11). The program ignores what it doesn't recognize in a crew rather than failing, instead of versioning crews separately.
15. Members never write real-looking secrets, even fake ones, so Claude's safeguards don't stop them by mistake (7.10). The rule is in the member protocol that the program ships, so every member in every crew follows it, and the orchestrator follows it in its own messages.
16. Each member can have its own model and effort (7.11). A member file can say `model:` and `effort:` at its top, `cadrei.conf` can set `MODEL=` and `EFFORT=` for the whole crew, and `cadrei up ... --model X --effort Y` overrides both for one start. With none of them set, a member gets Claude Code's own defaults, as today. The orchestrator doesn't take the crew's `MODEL` and `EFFORT`.
17. Cadrei is easy for other tools to build on, such as a website that draws a crew (7.13). `cadrei ls --json` (version 1) is a documented public interface with a compatibility promise: within a version, fields are only added, and a removal or a change of meaning bumps the version. `cadrei ls --json --watch` streams the same state as one JSON object per line, a full snapshot first and then each change, built on the hook state files and the 7.7 cache, never asking Claude. There's no built-in web server, for safety, and a new page, `docs/tools.md`, says why and shows how to read both.

**Naming.** Cadrei is the program, the `cadrei` command. A user's folder with its teams, members, playbook, projects and settings (for example `main`) is their **crew**, and teams and members live inside a crew. All copy in this spec says "crew" for it. Paths and identifiers keep the old word: `~/.cadrei/<name>`, `cadrei.conf`, `CADREI_HOME`, session names like `main-dev-...`, and the `ls --json` fields. The README and guide.md note that older docs and the folder layout say "cadrei" for a crew.

Made in this spec (each one can be changed before building):

- D1. Setup reads single key presses (Enter, `p`, `r`, `q`) in a real terminal and falls back to reading a line everywhere else (tests, pipes).
- D2. A missing or too old tmux stops the first run, since the team can't start without it. A Claude Code that isn't logged in doesn't stop it, because Claude Code asks for the login when it opens.
- D3. The git identity warning is one line on the first run. After that it shows only in `cadrei --check` and in the orchestrator's snapshot (5.1). Commits that skip for lack of an identity stay silent.
- D4. Cadrei writes a snapshot of the crew into the orchestrator's prompt on every launch. The greeting is built from it, so the orchestrator speaks first without running any command.
- D5. New commands, listed under a new "Setup" group in `cadrei help advanced`: `cadrei hook [on|off|skip]` and `cadrei tmux [on|off]`.
- D6. (Changed by decision 14.) The tmux choice is a crew setting, `ORCHESTRATOR` in `cadrei.conf`, with an optional override for one machine (4.6). An old `ORCHESTRATOR_TMUX=1` counts as `ORCHESTRATOR=tmux` when `ORCHESTRATOR` isn't set.
- D7. `--tmux` and `--detach` keep working as one-time overrides, and `--no-tmux` is new. `--detach` alone now implies `--tmux`.
- D8. Cadrei sets only per-session and per-window tmux options on its own sessions. It never binds keys, never sets server-wide options and never touches `~/.tmux.conf`. The hints use tmux's built-in keys.
- D9. A restore names the crew from its repo (`cadrei-main` becomes `main`) and asks for a name only when that one is taken.
- D10. The read-only review starter runs the reviewer only, and tells it to use no shell commands (overriding its role file's "run the code or the tests" rule for this task), so nothing asks for approval in a window the user can't see. If a prompt shows up anyway, the team line shows the reviewer as waiting on you.
- D11. `cadrei ls` shows what each running member is doing: starting, working, idle, waiting on you, or unknown (7.3). Cadrei learns it from Claude Code hooks in the member's settings copy, never by reading its screen (T4).
- D12. The plain fallback uses the ASCII marks `+ ! x`, the bullet `-` and the error prefix `cadrei:`.

## 2. Style system

### 2.1 Output modes

Each stream (stdout, stderr) picks its mode on its own:

| Mode | When | What it means |
|---|---|---|
| Styled | the stream is a terminal, `TERM` is set and isn't `dumb`, and `NO_COLOR` is unset or empty | colors, Unicode marks and bullets |
| Plain | otherwise | no escape codes, ASCII marks and bullets |

`FORCE_COLOR=1` (or `CLICOLOR_FORCE=1`) forces styled mode, for recordings such as `docs/demo.tape`. Tests run in plain mode.

### 2.2 Marks

| Meaning | Styled | Plain | Color |
|---|---|---|---|
| Done, or fine | `✓` | `+` | green |
| Needs you, or a heads-up | `!` | `!` | yellow |
| Failed, so cadrei stopped | `✗` | `x` | red |
| List item | `·` | `-` | dim |
| Member working (in `ls`) | `●` | `*` | green |
| Member idle (in `ls`) | `○` | `o` | default |
| Member waiting on you (in `ls`) | `!` | `!` | yellow |
| Member starting (in `ls`) | `◌` | `.` | dim |
| Member state unknown (in `ls`) | `?` | `?` | dim |
| Member stopped by safeguards (in `ls`) | `✗` | `x` | red |

A mark is never the only carrier of meaning: the words after it always say the state too.

### 2.3 Colors

Five styles and no more. They use the terminal's 16 base colors so they follow the user's theme.

| Style | Used for |
|---|---|
| bold | the product name in a screen header, section headings, the crew name in `ls` |
| dim | paths in parentheses, secondary notes, list bullets, "not running" |
| green | `✓`, `●` |
| yellow | `!` |
| red | `✗` |
| cyan | a command the user can type, when it stands alone or after "Run" or "with" |
| accent (bold clay) | the crew's name, in two places only: `✓ Created your crew main` (and the 3.11 and 7.8 equivalents) and the status bar's left label (6.2). It's the one "this is yours" color, from the brand (2.3.1). Under NO_COLOR, bold only. |

Body text stays in the terminal's default color.

#### 2.3.1 Brand colors in the terminal

The brand palette is "A. Clay": clay `#C2603E` on light and `#E27D58` on dark (`#A9502F` for small text on light), tmux green `#3D9F60` on light and `#5BC27D` on dark, ivory `#FAF8F4`, warm black `#171513` and ink `#1F1C19`. The logo is five dots in a V like `>_`: ink dots, a clay lead dot for the orchestrator, and a green cursor for "you".

The accent is the clay, and it's picked like this:

| Terminal | Background dark | Background light | Background unknown |
|---|---|---|---|
| truecolor (`COLORTERM` is `truecolor` or `24bit`) | `#E27D58` | `#A9502F` | `#C2603E` |
| 256 colors (`TERM` holds `256color`) | 173 | 130 | 166 |
| 16 colors or fewer | bold only | bold only | bold only |
| NO_COLOR, a pipe, `TERM=dumb` | (plain mode, 2.1) | | |

- **The background** comes only from `COLORFGBG` (set by some terminals as `fg;bg`): a last field of 0 to 6 or 8 means dark, 7 or 9 to 15 means light, and anything else, or no variable, means unknown. Cadrei doesn't ask the terminal (an OSC 11 query): that needs a round trip, tmux can swallow it, and a late answer can leak into what the user types.
- **Unknown uses `#C2603E`**, the brand's own clay, because it holds up on both sides: about 4:1 on typical dark backgrounds (5.0 on black, 4.0 on `#1E1E1E`) and on light ones (4.2 on white, 3.9 on ivory). It's always bold here, and it's never the only carrier of meaning. `#E27D58` drops to 2.9:1 on white, and `#A9502F` to 3.1:1 on `#1E1E1E`.
- **The 256-color picks** keep the clay's hue rather than the nearest dot by distance. 173 (`#D7875F`) for dark is nearest to `#E27D58`. 130 (`#AF5F00`) for light keeps 4.7:1 on white. 166 (`#D75F00`) for unknown gives 4.4:1 on `#1E1E1E` and 3.8:1 on white. The closest dot to `#C2603E` by distance, 131, is a dusty pink.
- **16 colors fall back to bold only.** Every ANSI color already means something here (green done, yellow needs you, red failed, cyan a command), and ANSI magenta and blue vary too much between themes to stand in for clay.
- **The marks stay theme colors.** `✓` and `●` keep ANSI green, and `!` and `✗` keep yellow and red. They form one set that follows the user's theme, and a truecolor brand green beside a theme yellow and red would look like a mistake. The brand green lives in the tmux status bar (6.1).

### 2.4 Layout

- **Screens** are what cadrei shows while setting up or opening: the first run, a restore, health findings on open, and the lines before Claude Code or tmux takes over. They have a 2-space left margin and one blank line between sections. A screen starts with a blank line.
- **Command output** (`ls`, `help`, `project add`, `up`, `stop`, `allow`) has no left margin for headings and 2 spaces for items.
- **Errors** go to stderr. Styled: `✗ <what happened>.` at column 0, then the fix on the next line indented 2 spaces. Plain: `cadrei: <what happened>.` then the fix the same way.
- **Width**: W = the terminal width, capped at 80. It's 80 when the width is unknown. Text wraps at word boundaries within W. A continuation line lines up with the text after the mark or bullet (a hanging indent). Paths, commands and URLs are never broken. If one alone is wider than W, it overflows.
- **Narrow terminals**: when the header's lines don't fit beside the mascot (under 70 columns for the first run), the header drops the art and its tagline wraps (3.7).

### 2.5 Paths

Every path goes through `display()` (`~` for the home folder, symlinks resolved) everywhere, including `up`, `allow`, `project add` and `project sync`, which print full paths today. Paths are never shortened with `...`.

### 2.6 Voice

- Follow the repo's CLAUDE.md: casual, "you", contractions, short sentences, plain words, no em dashes.
- Sentence case. Full sentences end with a period. Labels, list items and status lines don't.
- One idea per line. Lead with what happened, then what to do.
- Glossary, used the same way everywhere:

| Say | Not |
|---|---|
| your crew (the user's folder, for example `main`) | your cadrei, the cadrei, this cadrei. Cadrei is the program. Older docs and the folder layout (`~/.cadrei/<name>`, `cadrei.conf`, `CADREI_HOME`) still say cadrei for a crew. |
| your orchestrator | the orchestrator (when talking to the user) |
| your team, a team member | sessions, members (in screens; `members` stays in files and commands) |
| a project | a registered project, a registry entry |
| trusted in Claude Code | trust (alone, unexplained) |
| cadrei's instructions | the cadrei skill, the skill link |
| the every-chat hook | the orchestrator hook, SessionStart hook |
| a fresh chat | a new conversation |
| leave (tmux) | detach, step away |

## 3. First run

All first-run screens are written by a new `firstRun` that replaces today's question chain (`cmd/cadrei/setup.go`). Order: header, checks, plan, one key, the work, open.

### 3.1 New user inside a git repo (`~/code/my-app`)

80 columns, styled:

```text
$ cadrei

  +----------+  cadrei v0.2.1
  | lead art |  A team of Claude Code helpers you lead from one chat.
  +----------+  ~/code/my-app

  ✓ Claude Code 2.1.295 (logged in), git and tmux are ready

  Here's the plan
  · Create your crew main in ~/.cadrei/main, with an engineer and a reviewer
  · Add my-app as your first project
  · Trust both in Claude Code
    Your team works there without Claude Code asking first.
  · Link cadrei's instructions into Claude Code (~/.claude/skills/cadrei)
  · Open your orchestrator in tmux (recommended)
    It keeps going if you close this window. Ctrl-b s switch, Ctrl-b d leave

  Press Enter to set this up.
  Or press p for the plain terminal, r to restore from GitHub, q to quit.
```

**The header** is the compact mascot header (7.12.1): the tiny lead beside three lines, `cadrei v0.2.1`, the tagline, and the folder the user is in. Without art (fewer than 256 colors, plain mode, a pipe, or too narrow) the three lines stay, at the margin.

**The checks.**
- While they run (well under a second), one line shows: `  Checking your setup...`. When all pass, it's replaced in place by the single `✓` line above. Plain mode prints only the result line.
- The versions come from `claude --version`, `git --version` and `tmux -V`. Only Claude Code's version is shown, since it's the one with a minimum that matters to the user.
- When any check fails or warns (a `✗` or a `!`), the line expands into the 3.5 rows under a `Checking your setup` heading.

**The plan.**
- One line per item. A dim "why" line sits only under the trust item and the tmux item. With a project, that's eight lines under the heading, and every change outside `~/.cadrei` is still named: the trust marks in `~/.claude.json`, and the skill link.
- `main` in the first item is the crew's name, drawn in the accent style (2.3).
- The keys in the tmux why line come from the user's real tmux prefix (`Ctrl-a s switch, Ctrl-a d leave` with `C-a`). There's no separate tutorial step any more: the same keys stay in the status bar (6.2), and the greeting offers more (`New to tmux? Ask me how to get around.`).

**When Enter may add the folder.** Trusting a folder in Claude Code does two things: Claude Code stops asking before it works there, and it starts using the repo's own Claude Code settings, which can run commands (hooks) and add tools (MCP servers) for every team member. A repo the user just cloned from someone else can hold those. So Enter adds the folder only when the repo has none of these:

- `.claude/settings.json`, `.claude/settings.local.json` or `.mcp.json` at its top;
- in any folder of the repo, at any depth, a `.claude/skills`, `.claude/agents` or `.claude/commands` folder with anything in it, because Claude Code loads a nested folder's skills when a member works on a file under it;
- a `.claude` that's a link, because it can point anywhere;
- for a linked worktree (a folder `git worktree add` made), the same in the main checkout: its `.claude/skills`, `.claude/agents` or `.claude/commands` with anything in it, a linked `.claude`, or its `.claude/settings.json` or `.claude/settings.local.json`, because Claude Code reads these from the main checkout; for a linked worktree of a submodule, the main checkout is the submodule's own, and the superproject walk below starts there;
- for a submodule, the same in every folder from the submodule up to its superproject's top (and on up through a submodule of a submodule), with `.claude/settings.json` and `.claude/settings.local.json` at each superproject's top (Claude Code's docs don't say it skips the shared one there, so it counts). Claude Code may take the superproject for the repository whose skills and local settings it loads, so cadrei checks it as if it does. The submodule itself is checked like any repo.

The check skips `.git` and the folders git ignores (except the repo's own top `.claude`, which Claude Code loads anyway), and it matches names in any case. A repo with more than 200,000 folders counts as having settings, because the rest wasn't checked (`Risky` in `internal/runtime/claude/claude.go`). For a worktree or a submodule, git is asked where the main checkout and the superproject are, with the repo's own hooks and fsmonitor turned off, so nothing in the repo runs. Most repos have none of these, so this keeps "one plan, one yes". A repo's `CLAUDE.md` alone doesn't count: it's instructions, it runs nothing, and members still ask before acting.

When the repo has any of them, the project is left out, the trust item covers only the crew, and a note takes the project's place:

```text
  Here's the plan
  · Create your crew main in ~/.cadrei/main, with an engineer and a reviewer
  · Trust it in Claude Code
    Your orchestrator opens there without Claude Code asking first.
  · Link cadrei's instructions into Claude Code (~/.claude/skills/cadrei)
  · Open your orchestrator in tmux (recommended)
    It keeps going if you close this window. Ctrl-b s switch, Ctrl-b d leave

  ! my-app has its own Claude Code settings (.mcp.json), which would run
    for your team once it's trusted. So it's left out.

  Press Enter to set this up.
  Or press a to add it, p for the plain terminal, r to restore, q to quit.
```

- The note names the files it found, separated by commas. When the list is long it wraps under the note's text.
- `a` adds the project. In a terminal, the plan is redrawn in place (from `Here's the plan` down; the header and checks stay), not printed again below:

```text
  Here's the plan
  · Create your crew main in ~/.cadrei/main, with an engineer and a reviewer
  · Add my-app as your first project
  · Trust both in Claude Code
    ! my-app's own settings (.mcp.json) will run for your team too.
  · Link cadrei's instructions into Claude Code (~/.claude/skills/cadrei)
  · Open your orchestrator in tmux (recommended)
    It keeps going if you close this window. Ctrl-b s switch, Ctrl-b d leave

  Press Enter to set this up.
  Or press a to leave it out, p for the plain terminal, r to restore, q to quit.
```

- `a` again toggles back to the screen before. In plain mode (no cursor control), the new plan is printed below instead.
- The prompt lines say "it", not the project's name, so they fit 80 columns whatever the name.
- Left out, the folder can be added later by asking the orchestrator, which brings the same warning to the user (5.7).
- Choosing the plain terminal or restoring doesn't change the project line.

Why this design: it trusts nothing a bare Enter shouldn't, it doesn't need GitHub or a network check (an origin "owned by you" can't be known offline, and forks blur it), and the common case stays one key.

**After Enter** (tmux chosen, not already inside tmux):

```text
  ✓ Created your crew main
  ✓ Added my-app as a project
  ✓ Trusted both in Claude Code
  ✓ Linked cadrei's instructions into Claude Code

  Opening your orchestrator in tmux.
```

- Then tmux takes the screen at once. There's no second Enter: the keys were already in the plan, and they stay in the status bar.
- `main` in `✓ Created your crew main` uses the accent style.
- Cadrei trusts `~/.cadrei/main` in Claude Code as part of creating it (T9), the same way it trusts a project folder, so Claude Code doesn't ask. When it can't (Claude Code hasn't made its config file yet, or the trust write is skipped for safety), the `✓ Trusted` line becomes:

  ```text
  ! Claude Code will ask to trust ~/.cadrei/main when it opens. That's your
    crew's own folder, so say yes.
  ```

  In that case cadrei waits for `Press Enter to open your orchestrator.` before tmux clears the screen, so the line gets read.

After `p` (plain terminal), the same `✓` lines, then:

```text
  Opening your orchestrator here. Your team still runs in tmux, and you can
  watch any of them with cadrei attach.
```

Then Claude Code opens in this terminal with no extra key press. The plan's tmux line is saved as `terminal` (4.6).

`q`, Ctrl-C or Ctrl-D at the plan:

```text
  Nothing was changed.
```

Exit code 1. Any other key is ignored and the prompt stays.

Same as 3.1, with no project and the trust item for the crew alone:

```text
  Here's the plan
  · Create your crew main in ~/.cadrei/main, with an engineer and a reviewer
  · Trust it in Claude Code
    Your orchestrator opens there without Claude Code asking first.
  · Link cadrei's instructions into Claude Code (~/.claude/skills/cadrei)
  · Open your orchestrator in tmux (recommended)
    It keeps going if you close this window. Ctrl-b s switch, Ctrl-b d leave
```

And the work lines are:

```text
  ✓ Created your crew main
  ✓ Trusted it in Claude Code
  ✓ Linked cadrei's instructions into Claude Code

  Opening your orchestrator in tmux.
```

The folder is "outside a git repo" when `git rev-parse --show-toplevel` fails, or the folder is inside `~/.cadrei`, or its name isn't a valid project name. In that last case a note follows the plan:

```text
  ! This folder's name (my app) can't be a project name. Ask your
    orchestrator to add it under another name.
```

### 3.3 Already inside tmux

The checks and the plan are the same, except the tmux item:

```text
  · Open your orchestrator as its own tmux session (recommended)
    It keeps going on its own. Ctrl-b s switch, Ctrl-b L back to here
```

After Enter, the work lines end with `Switching to your orchestrator.`, and the client switches at once. There's no separate tutorial. Mouse scrolling is on in cadrei's sessions only.

Every cadrei tmux call names one server with `-S <path>`: the socket `CADREI_TMUX_SOCKET` names, else tmux's default socket (`${TMUX_TMPDIR:-/tmp}/tmux-<uid>/default`). Today cadrei passes no `-L` without `CADREI_TMUX_SOCKET`, so tmux follows `$TMUX` and creates sessions on whatever server the user is in (T7). When the part of `$TMUX` before the first comma is that same path, cadrei creates the session there and switches the client to it (`switch-client`), so tmux never opens inside tmux. When it's another path, cadrei never runs `switch-client` (that would move a different client on cadrei's server). It opens the orchestrator in the current pane and says:

```text
  ! You're in tmux on another server, so your orchestrator opens right here
    this time.
```

### 3.4 Restore from GitHub (`r` at the plan)

```text
  Restore your crew from GitHub

  Which repo holds it? (owner/repo, or a URL) you/cadrei-main

  Here's the plan
  · Copy you/cadrei-main into ~/.cadrei/main
  · Link cadrei's instructions into Claude Code (~/.claude/skills/cadrei)
  · Open your orchestrator in tmux (recommended)
    It keeps going if you close this window. Ctrl-b s switch, Ctrl-b d leave

  Press Enter to set this up.
  Or press p for the plain terminal, q to quit.
```

- The repo question is a line read (it needs typing). An empty answer asks again, up to 3 times, then shows `Nothing was changed.` An answer starting with `-` gets `! A repo name can't start with -.` and asks again.
- The name comes from the repo (D9). When `~/.cadrei/<name>` exists or the name is taken, this line is added before the plan, and the plan uses the answer:

```text
  You already have a crew called main. Name for this one? 
```

After Enter:

```text
  Copying you/cadrei-main...
  ✓ Restored your crew main into ~/.cadrei/main
  ✓ Linked cadrei's instructions into Claude Code
```

When the copy fails, nothing is kept:

```text
  ✗ Couldn't copy you/cadrei-main: <git's reason, one line>.
```

### 4.6 Settings

The tmux choice is a setting of the crew (decision 14): `ORCHESTRATOR=tmux` or `ORCHESTRATOR=terminal` in its `cadrei.conf`, committed with it, so it travels with a backup and a restore.

- One machine can differ: `cadrei tmux on|off --here` writes the key to `.claude/local/cadrei.conf` instead (git-ignored, 7.9.1), which wins over `cadrei.conf` on this machine only. `cadrei tmux` says where the value comes from: `Your orchestrator opens in tmux (this machine only).`

## 5. The orchestrator side

### 5.1 Launch

The prompt file (today: `orchestrator.Prompt`) keeps only static text, because Claude Code doesn't read it again on `--resume` (T2). The live snapshot comes from a `SessionStart` hook instead. Cadrei writes an orchestrator-only settings file, `<build>/orchestrator-settings.json`, holding a `SessionStart` hook that runs `<cadrei> hook snapshot` and a `UserPromptSubmit` hook that runs `<cadrei> hook team-status` (5.8), and passes it with `--settings`.

**Every hook command cadrei writes** (the every-chat `SessionStart` hook in `~/.claude/settings.json`, the orchestrator-only settings, and a member's settings copy) has this exact form, with the program's path quoted as today's `quote()` does:

```text
test -x '/opt/homebrew/bin/cadrei' && '/opt/homebrew/bin/cadrei' hook team-status 2>/dev/null; exit 0
```

- When the program is gone (a `brew uninstall cadrei` without `cadrei uninstall`, or an `rm`), `test` fails and the shell exits 0 having printed nothing.
- There's no `exec`: a non-interactive shell would exit at a failed `exec` before reaching `exit 0`. Without it, the `; exit 0` always runs, so whatever cadrei itself returns, the hook ends with exit 0. A downgrade (an older cadrei at the same path that doesn't know `hook team-status`, `hook snapshot` or `hook state`) therefore shows nothing: its error goes to `2>/dev/null`, and cadrei's hooks never write to stderr themselves (T14). The hook's JSON on stdin still reaches cadrei.
- `test` is a shell builtin, so the check costs no extra process and stays within T14's few milliseconds.
- `hookFindings`, `hooks.Find`, `hooks.Set` and `Unhook` must read three forms: the bare `<bin> hook <sub>` of 0.2.0, the in-between `test -x <bin> && <bin> hook <sub>; exit 0` (this form without `2>/dev/null`, which cadrei wrote before it), and this one. They rewrite either older form to this one (asking first, as the health check does for the every-chat hook in `~/.claude/settings.json`; without asking for cadrei's own settings copies).
- The git pre-push guard is the one exception: it keeps failing closed when the program is missing, because it's a safety check. Its message then says `cadrei is missing, so this check can't run. Reinstall cadrei, or remove .git/hooks/pre-push.`

Cleaning up after `brew uninstall`: Homebrew has no uninstall step a formula can run, so cadrei can't remove its hooks then. Instead:
1. The formula's caveats (`packaging/homebrew/cadrei.rb.in`) add: `To remove cadrei, run cadrei uninstall: it removes its hooks and links, then the program.`
2. Every `cadrei uninstall` removes a Homebrew install itself, as its plan's last step (7.8.8).
3. Leftover hooks are harmless no-ops (above), and reinstalling cadrei puts them right on the next run.

**The snapshot.** `hook snapshot` prints the block below to stdout. Claude Code adds that to the model's context on startup and on resume (and after `/clear` and `/compact`), and nothing shows in the chat. Members never get this file. The every-chat hook (`hook orchestrator`) prints the same block, so an orchestrator started that way gets the snapshot too (but not the team line, 5.8).

```text
## Right now

- Crew: main (~/.cadrei/main)
- Opened by: cadrei, at 14:02 on 2026-10-09
- First run: yes
- Orchestrator opens in: tmux (prefix C-b; the user is not inside another tmux)
- Opened from: the project my-app (~/code/my-app)
- Projects: my-app (present, team dev)
- Teams: dev (engineer, reviewer); running: none
- Members: none running
- Stopped by safeguards: none
- One-time grants left over: 0
- Every-chat hook: off (never offered)
- Git identity: missing
```

Field rules:

- `Crew`: the crew's name and path. The greeting (5.2, 5.3) names it.
- `First run`: `yes` while the state key `first_task_pending` is set in `~/.cadrei/config`. The first run sets it, and the first `cadrei up` that starts a member clears it. So a user who quits the first chat early, or whose first chat went through the login, still gets the first-run greeting next time. A restore never sets it. Otherwise `no`.
- `Opened from`: `the project <name> (<path>)`, or `a git repo that isn't a project: <path>`, or `your home folder`, or `another folder: <path>`.
- `Every-chat hook`: `on`, `off (never offered)` or `off (the user said no)`.
- `Git identity`: `set` or `missing`.
- `Stopped by safeguards`: `none`, or each running member in that state with its session name and when it stopped, for example `the engineer on my-app (main-dev-my-app-engineer), since 14:20`. It's checked on every snapshot, for every running member (7.7).
- `Members`: each running member with its 7.3 state, for example `dev on my-app: engineer working for 4m, reviewer waiting on you for 1m`. Under a minute it's `working just now`, never `working for just now`.
- `Projects` lists each project with its `state` from `ls --json`.

Cadrei launches Claude Code with a seed message as the first prompt (T1). If Claude Code runs a positional slash command as a skill (T23), the seed is `/cadrei`: it's drawn as a command rather than as typed text, and it loads the skill. Otherwise it stays the text below, as the fallback. The seed is always the last argument, after `--`, because `--allowedTools` takes every following word as a rule and would swallow it. It shows in the chat as a normal user message (there's no way to hide it), so its text stays short and honest:

```text
(cadrei opened this chat)
```

The argv ends with `-- "(cadrei opened this chat)"`. The seed also works with `--resume` (tested on 2.1.268 and 2.1.295). Every time cadrei opens the orchestrator, a new chat or a resumed one, it sends the seed, so the orchestrator always says who it is and which crew it's for (5.3). (This replaces the review's "skip the seed on a quiet resume": with the 5.3 header there's always something worth saying, and the user wants the orchestrator to make itself known every time. The cost is one short visible user message per open.) The one exception is a chat whose last user record is already a seed with no reply after it: the earlier open never got its greeting, so that seed is still waiting, and cadrei resumes without adding a second one, which would show twice. Claude Code doesn't answer a waiting message on its own, so then the greeting comes after the user's first message. On a tmux reattach no seed is sent, because the chat is still running.

The orchestrator also gets `--allowedTools` with these exact rules, and only the orchestrator (T3):

```text
Bash(cadrei ls)
Bash(cadrei ls --json)
Bash(cadrei ls --all)
Bash(cadrei ls --json --all)
Bash(cadrei ls --all --json)
Bash(cadrei allow)
Bash(cadrei allow list)
Bash(cadrei hook skip)
```

These eight exact forms run without asking. `cadrei hook skip` only records the user's no to the 5.5 offer, so the no doesn't lead to a permission prompt. Anything else, including other flags, a redirect, a pipe or `&&`, still asks (T3). Members' `--settings` copies are untouched. An orchestrator started by the every-chat hook can't get these flags, so it keeps asking for these commands.

### 5.5 The every-chat hook offer

- When: right after the orchestrator relays the first finished task in a chat, if the snapshot says `off (never offered)`.

### 5.8 The team status line

While any member runs, the orchestrator ends every reply with one short line about the team. It's how the user always knows who's busy without asking.

#### 5.8.1 Where the data comes from

- The orchestrator-only settings file (5.1) has a `UserPromptSubmit` hook that runs `<cadrei> hook team-status`.
- It runs on every user message, and on every member reply too, since a cross-session message arrives as `UserPromptSubmit` (T4).
- The hook builds the team's state with the same code as `cadrei hook snapshot` and `cadrei ls --json`: running sessions, the 7.3 states, and the 7.7 safeguard check. The safeguard check uses the per-member cache (7.7), so a prompt rereads a transcript only when it changed.
- It prints a short block to stdout. Claude Code adds that to the model's context for this turn (T14 saw that `UserPromptSubmit` stdout goes into the context), and nothing shows in the chat.
- The orchestrator reads it and needs no tool call.
- Every-chat hook orchestrators get no team line: the team status hook lives only in the orchestrator-only settings that plain `cadrei` passes, and the every-chat hook can't add settings to a chat. They already lack the pre-allowed commands for the same reason. The skill tells such an orchestrator to run `cadrei ls` when it needs the team's status (5.8.4). `cadrei hook on` and `off` manage only the one `SessionStart` entry, as before.

What the hook prints, with members running:

```text
## Team status (from cadrei, not the user)
End your reply with this line, exactly, after a blank line:
Team: **✗ scout stopped by safeguards** · **! writer waiting on you** · engineer working 25m · designer idle
```

When the crew's `playbook.md` has the hide rule (5.8.5; the hook looks for the line `Don't end replies with the team status line.`), the block says so itself:

```text
## Team status (from cadrei, not the user)
playbook.md hides the team line, so don't add it. Status only:
Team: **! writer waiting on you** · engineer working 25m · designer idle
```

The first time the line shows on this machine, the block has two more lines (5.8.6):

```text
## Team status (from cadrei, not the user)
End your reply with this line, exactly, after a blank line:
Team: engineer working 4m
First time only: right under it, add exactly:
(Say "hide the team line" if you'd rather not see this.)
```

With no member running:

```text
## Team status (from cadrei, not the user)
No member is running, so no team line.
```

The hook writes the finished line and the instruction itself on every message, so neither depends on the model remembering the skill. Both survive a long chat and `/compact`, because each prompt brings them in fresh. The block stays at three to five short lines.

The hook follows T14's rules:

- It always exits 0 and never blocks the prompt.
- It has `"timeout": 5` and runs synchronously.
- It recovers from panics and takes no locks.
- Budget: under 50 ms with 10 members, and with 30 members whose transcripts are 256 KB each (T17).
- On any error, or past its own 2-second limit, it prints nothing. The orchestrator then leaves the line out, and the chat goes on as normal.

#### 5.8.2 The line

`Team: ` then the members, separated by ` · `. Order:

1. stopped by safeguards: `**✗ <role> stopped by safeguards**`
2. waiting on you: `**! <role> waiting on you**`
3. working, the longest first: `<role> working <duration>`, plus ` (quiet <duration>)` with the no-activity note
4. starting: `<role> starting`
5. unknown: `<role> running`
6. idle: `<role> idle`

- The first two are bold (Claude Code draws a reply's Markdown) and keep their marks. The rest have no marks, to stay calm.
- A role that runs in two places gets its project or team: `engineer (my-app)`, `engineer (blog)`.
- Durations are 7.3's: `just now`, `4m`, `1h 5m`.
- Length: when the line would be longer than 120 characters, the calm members fold into counts (`4 working · 3 idle`). Waiting and stopped members always stay by name. Past 3 of those, the rest fold into `+2 more need you`. So the line is one line, or two when it wraps on a narrow screen.

#### 5.8.3 Exact copy

| Case | Line |
|---|---|
| No member running | (no line) |
| One working | `Team: engineer working 4m` |
| One idle | `Team: engineer idle` |
| Several | `Team: engineer working 25m · reviewer working 3m · designer idle` |
| One waiting | `Team: **! writer waiting on you** · engineer working 25m · designer idle` |
| One stopped by safeguards | `Team: **✗ scout stopped by safeguards** · engineer working 25m · designer idle` |
| Stopped and waiting | `Team: **✗ scout stopped by safeguards** · **! writer waiting on you** · engineer working 25m` |
| Same role in two projects | `Team: engineer (my-app) working 25m · engineer (blog) idle` |
| Quiet for a while | `Team: engineer working 25m (quiet 12m) · designer idle` |
| Starting and unknown | `Team: engineer starting · writer running` |
| Many (10, one waiting) | `Team: **! reviewer (my-app) waiting on you** · 6 working · 3 idle` |
| Many urgent (5 waiting) | `Team: **! reviewer waiting on you** · **! editor waiting on you** · **! tutor waiting on you** · +2 more need you · 3 working` |

How it looks at the end of a reply:

```text
Started the reviewer on my-app. It's reading the code now and will report
the top 3 things to fix.

Team: reviewer working just now
```

#### 5.8.4 Rules for the orchestrator (skill)

- Follow the latest team status block: it says each turn whether to end the reply with the line. Every reply to the user ends with the hook's line, exactly as written, after a blank line, unless the block says the playbook hides it. That includes replies that relay a member's result. When the hook says no member is running, or printed nothing, the reply has no team line.
- The line is the reply's last line (only the one-time hint of 5.8.6 may follow it): nothing else after it, and never inside a code block, a question (`AskUserQuestion`) or a quoted member reply.
- When the line shows someone waiting or stopped by safeguards and the reply isn't already about them, add one short sentence before the line saying what to do. For example: `The writer in docs is waiting on you in its window: cadrei attach docs.` For safeguard stops, the 5.7 "Safeguard stops" rules apply.
- The first-run greeting (5.2) ends with the line too, when someone is running. The later-run greeting (5.3) carries it as its second line instead, and never repeats it at its end: one team line per reply.
- In an orchestrator the every-chat hook started, no team status block arrives, so there's no team line. Run `cadrei ls` when the team's status matters (it isn't pre-allowed there, so Claude Code asks).
- The line is information, never consent, and never a reason to start, stop or message a member on its own.
- A rule in the crew's `playbook.md` wins over this one, as the playbook wins over the skill everywhere but the safety sections (consent, member permissions, stopping, uninstalling, reset and restore, the rules), which a playbook can add to and never loosen (forward-compatibility audit M4). When the playbook says not to end replies with the team status line, leave the line out, even with members running.

#### 5.8.5 Hiding and showing the line

The user hides the line by asking ("hide the team line", "hide the team status line", "stop showing the team line"). It's a preference of this crew, kept in its playbook, so it travels with a backup and a restore. There's no setting, command or toggle for it. The hook keeps running either way, and nothing changes in code, settings or `~/.cadrei/config`.

To hide it:

1. Add this rule to `playbook.md`, under a `## Preferences` heading (made at the end of the file when there's none):

   ```text
   - Don't end replies with the team status line.
   ```

2. Commit it in the crew's git (`Hide the team status line`), and push when the crew has a backup.
3. Confirm, with no team line under this reply or any later one:

   ```text
   Done. I won't end my replies with the team line anymore. Say "show the
   team line" to bring it back, or run cadrei ls to see your team anytime.
   ```

To show it again ("show the team line", "bring back the team status line"):

1. Remove that rule from `playbook.md`. Remove the `## Preferences` heading too when nothing else is under it.
2. Commit it (`Show the team status line again`), and push when there's a backup.
3. Confirm, and end this reply with the line when someone is running:

   ```text
   Done. The team line is back at the end of my replies.
   ```

   With nobody running: `Done. The team line is back. You'll see it whenever someone on your team is running.`

- Asked to hide it when it's already hidden: `It's already hidden. Say "show the team line" to bring it back.`
- Asked to show it when it's already shown: `It's already on. It shows whenever someone on your team is running.`
- Hidden or not, the 5.7 rules for someone waiting or stopped by safeguards still apply: the orchestrator still tells the user in words. Only the line itself goes.

#### 5.8.6 The one-time hint

The first time the line shows for a user, the orchestrator adds a hint right under it, once:

```text
Started the reviewer on my-app. It's reading the code now and will report
the top 3 things to fix.

Team: reviewer working just now
(Say "hide the team line" if you'd rather not see this.)
```

- "The first time" means the first block on this machine that holds a team line: a marker file, `~/.cadrei/config/team-line-hint`, that doesn't exist yet. It's per machine and covers every crew on it.
- This is the one bit of code the hint needs, kept tiny inside `hook team-status`. When it prints a team line and the marker is missing, it adds the two hint lines to the block (5.8.1) and creates the marker in the same run. Every later block has no hint.
- When the crew's `playbook.md` already has the hide rule (a plain text match on `Don't end replies with the team status line.`), the hook adds no hint and creates no marker, so the hint waits until the line actually shows.
- If creating the marker fails, the hook prints no hint, so it never repeats on every reply.
- `cadrei uninstall` removes `~/.cadrei/config`, and the marker with it, so a fresh install shows the hint once again.
- The orchestrator copies the hint exactly, as the reply's last line, right under the team line with no blank line between. It never adds the hint on its own, without the hook's block asking.
- The same hint shows in the moving-around answers (5.6), and guide.md says it too (9.1).


## 6. tmux, gentle by default

### 6.1 What cadrei sets

Only on cadrei's own sessions (the orchestrator's and every team's), with `set-option -t <session>` or `-w -t <window>`. The user's `~/.tmux.conf` and server-wide options are never touched (D8).

| Option | Scope | Value |
|---|---|---|
| `mouse` | session | `on` |
| `status` | session | `on` |
| `status-position` | session | `bottom` |
| `status-style` | session | `bg=#3D9F60,fg=#1F1C19`: the brand's green bar with ink text (5.1:1, the same on dark and light themes because the bar has its own background). tmux turns these into the nearest 256 colors on a terminal without RGB. Under NO_COLOR: `bg=default,fg=default`. |
| `status-left` | session | ` #[bold,bg=#A9502F,fg=#FAF8F4] main #[default] ` for the orchestrator's session: the crew's name on a clay block, ivory on the darker clay (5.1:1), like the logo's clay lead dot on the green. For a team's session: ` #[bold,bg=#A9502F,fg=#FAF8F4] main #[default] dev on my-app `. Under NO_COLOR, ` #[bold]main#[nobold] `. |
| `status-left-length` | session | `40` |
| `status-right` | session | see 6.2 |
| `status-right-length` | session | `60` |
| `window-status-format` | window | ` #W ` |
| `window-status-current-format` | window | ` #[bold]#W#[nobold] ` |
| `history-limit` | session, before its real window exists | `50000` (see below) |
| `monitor-bell` | window | `on` |
| `aggressive-resize` | window | `on` |

Use only these option names. A server option set with `-t <session>` silently changes the whole server (T10 saw it with `focus-events`), so acceptance 22 checks `show-options -s` and `-g` stay the same.

`history-limit` only applies to windows made after it's set, and on tmux 3.2 the first window of `new-session` keeps the old value. So cadrei creates each session with a placeholder window, sets `history-limit`, creates the real window, and then kills the placeholder. Cadrei targets windows by name, so the real window's index (1) doesn't matter.

`allow-passthrough` is left out: Claude Code sends no notification sequences inside tmux by default (6.4), and tmux 3.2 doesn't have the option.

The bar stays calm: one green bar, one small clay block, and ink text. No other colors, and the current window is shown in bold only. Under NO_COLOR the `#[...]` style codes are left out. Today's `client-attached` display-message is removed, since the bar shows the keys all the time.

It costs about 4 ms per call. The orchestrator gets none of these hooks. `cadrei stop` removes the member's state file.

### 7.7 Safeguard stops

When Claude's safeguards stop a member's response, the member sends no reply, the orchestrator only gets an idle notice, and the user has to open the member's window and pick the model again by hand. Today nothing in cadrei notices, and `cadrei up` resumes such a chat without a word.

**What Claude Code writes.** The stop is a record in the session's transcript (`<config>/projects/<folder>/<session id>.jsonl`):

- `"type": "system"`, `"subtype": "informational"`, `"level": "notice"`
- `"content"` starting with `<model name>'s safeguards stopped the response above`. Seen so far: `... · continuing once with that noted`.
- Before it, an assistant record with `"stop_reason": "refusal"` (in most cases seen). After it, a user record with `"isMeta": true` that Claude Code adds itself.
- Claude Code then tries once more on its own. In the cases seen, the next assistant reply came 8 to 24 seconds later. When that try produces no reply, the member is stuck.

**The matcher.** A record is a safeguard stop when `type` is `system`, `subtype` is `informational`, and `content`, lowercased, contains `safeguards stopped the response`. It never looks at the model name: the name in the text changes, and the session can still show the same model afterwards. `level` isn't required, so a change there doesn't break it.

**Stopped.** A member is stopped by safeguards when, in its current transcript:

1. the last safeguard stop has no assistant record after it whose `stop_reason` isn't `refusal` (a normal reply, from any model), and
2. either the member is idle, or that stop is at least 60 seconds old.

Or, as a second signal that doesn't depend on the notice's wording: the last assistant record has `"stop_reason": "refusal"`, has no normal assistant reply after it (even with no notice), and the same second condition holds.

"Idle" here means the member's state file (7.3) says idle from a `Stop` or `StopFailure` whose time is after the stop record's timestamp. Then Claude Code's own retry has already finished, so there's no wait: the member is marked at once, and the idle notice that wakes the orchestrator already finds it stopped by safeguards. The 60-second wait only applies while the member is still working (or its state is unknown), to give that retry its chance.

A later normal reply clears it, so does a fresh chat (a new transcript), and so does stopping the member.

**Cache.** The result is kept per member in `<build>/state/<name>.safeguard` (written with a temp file and a rename), keyed by the transcript's path, size and modification time. The tail is read again only when one of those changed. So the team status hook (5.8), `cadrei ls` and the snapshot don't reread unchanged transcripts on every prompt.

**Where the transcript is.** The path comes from the member's state file (`transcript_path`, 7.3) when there is one, else from its session record (`<build>/sessions/<name>.json`: session id and folder) through the runtime's transcript lookup. Cadrei reads only the last 256 KB, drops the first partial line, and skips lines that aren't valid JSON. A missing or unreadable transcript means "not stopped".

**Check 1: on start.** After `cadrei up` starts or resumes a member, it runs the check on that member's transcript, without the 60-second wait (nothing is retrying in a chat that was just resumed). A fresh chat has no transcript and is never flagged. Styled:

```text
  Open its window and pick the model again: cadrei attach dev my-app
  Or start it fresh: cadrei stop dev/engineer my-app --fresh
  then cadrei up dev/engineer my-app
```

Plain:

```text

! Claude's safeguards stopped the engineer's last reply, so it won't answer.
  Open its window and pick the model again: cadrei attach dev my-app
  Or start it fresh: cadrei stop dev/engineer my-app --fresh
  then cadrei up dev/engineer my-app
```

- With no project: `cadrei attach dev`, `cadrei stop dev/engineer --fresh` and `cadrei up dev/engineer`.
- The fix names `stop --fresh` then `up` because the member is already running by then, and `cadrei up --fresh` on a running member only says it's running.
- Each flagged member gets its own `!` block, after all the start lines.
- The exit code stays 0: the member did start.

### 7.8 Archive and restore

The user's goal: try a new version of cadrei as a brand-new user, then later get their old setup back exactly.

- **System cadrei**: everything machine-level. That's the program, `~/.cadrei/framework`, `~/.cadrei/config` (the default crew, the projects folder, the places map, the permissions fingerprint, the tmux choice, state and markers), the skill link, and the hooks.
- **Private cadrei**, now called your crews: the crew folders, `~/.cadrei/<name>`.

Today `cadrei uninstall` removes the system parts but keeps the crews, so a reinstall isn't a first run, and the places map is lost.

#### 7.8.1 `cadrei uninstall --archive`

It does what `cadrei uninstall` does, and also moves every crew and `~/.cadrei/config` into one new archive. Nothing is deleted outright. Afterwards `~/.cadrei` doesn't exist, so `brew uninstall cadrei`, `brew install rafi-ramdhani/cadrei/cadrei` and then `cadrei` is exactly a new user's first run (plus the 3.10 offer).

The archive: `~/.cadrei-archive/<YYYY-MM-DD-HHMM>/`, holding:

- `cadreis/<name>/`: each crew folder, moved (renamed) whole, `.git`, `.claude/build`, session records and all.
- `config/`: `~/.cadrei/config`, moved whole.
- `other/`: anything else that was in `~/.cadrei` (not `framework`), moved, so `~/.cadrei` can go.
- `manifest.json`: `version` 1; `archived_at`; `cadrei_version`; `home` (the home folder); `cadreis` (each `name`, `path`, `default`, and `backup`: `remote`, plus `is_pushed` and `has_uncommitted` as checked); `machine` (`every_chat_hook` on or off, `skill_linked`, `orchestrator` tmux or terminal); `steps` (each step as it finishes, for T-A1); `restored_at` (null until restored).

- `--yes` skips the final question and pushes nothing. Each crew that's behind its backup gets `! work's 2 commits weren't pushed (--yes doesn't push).`
- Running sessions are stopped as part of the plan, after the user's yes, as `cadrei uninstall` does.
- An orchestrator open in a terminal stops it: `✗ Your orchestrator is open in another terminal (open since 14:02). Close it first, then run this again.` Its folder is about to move.
- Run from inside an orchestrator (`CADREI_ORCHESTRATOR=1`): `✗ Run this in a terminal, not from your orchestrator. It moves the orchestrator's own folder.` Members are refused as usual.
- A crew outside `~/.cadrei` (only reachable through `CADREI_HOME`) isn't moved. The plan says `! ~/work/cadrei isn't in ~/.cadrei, so it stays where it is.`
- When `~/.cadrei/config` is a link, the link is moved and its target stays, as `cadrei uninstall` handles links today.
- Moving is a rename, both folders being under the home folder. When a rename fails (another disk, T-A1), cadrei copies, checks the copy, then removes the original, and records each step in `manifest.json` so a second run picks up where it stopped.
- Never touched: projects, `~/.claude.json` (trust marks), `~/.claude/projects` (chats), and the user's Claude Code settings beyond the every-chat hook entries.
- Members are denied reading or editing `~/.cadrei-archive` (added to the fixed denies, with its physical path).

#### 7.8.7 `cadrei uninstall --all` (decided: added in 0.2.1)

A deliberate way to remove everything. Plain `cadrei uninstall` still never deletes a crew, and that stays the default. `--all` does what `cadrei uninstall` does, then deletes every crew folder, `~/.cadrei` (cadrei's settings, state and program files, and anything else in it), and `~/.cadrei-archive` with every archive. It also removes the crews' trust marks in Claude Code. With Homebrew it removes the program too, as its plan's last step (7.8.8), unless `--keep-program` is given; otherwise the last line says how to remove the program. Nothing of cadrei is left.

- **Project folders are never deleted.** They're the user's work, and cadrei only links them. A project whose folder is inside what it deletes (`~/.cadrei`, `~/.cadrei-archive`) stops it before anything is deleted, checked in every crew's places and 0.2.0's, and again after the typed yes and the stop, with each crew's places locked until it's deleted. A crew's places or projects file it can't read stops it too (`Couldn't read <file>, so this can't check that no project's folder is in what it deletes: <why>. Nothing was deleted.`), and so does a crew made meanwhile: `The project <name>'s folder, <path>, is inside ~/.cadrei, which this deletes.` with `Move it out and link it again with cadrei project link <name> <folder>, then run this again.`
- **A link loses only the link.** When `~/.cadrei` or `~/.cadrei-archive` is a link, the link is removed and the folder it points to stays. In a linked `~/.cadrei`, the crews and cadrei's own `config` and `framework` folders are deleted, and anything else there stays; a project there that isn't in a crew is fine. Nothing is ever deleted through a link inside a crew. A crew is a folder with `members/` and a `cadrei.conf` or `playbook.md`, so a folder of the user's own with a `members/` folder isn't taken for one.
- **The plan comes first, every time.** It names each step: the members it stops, the links and hook it removes, each crew with what it holds (`delete the crew work (~/.cadrei/work): 1 team, 2 members, 1 project (their folders stay)`), `~/.cadrei` with anything in it that isn't a crew, the archives, and the trust marks. Then `It keeps every project's folder: app (~/src/app). Claude Code's own chat history stays too.` Then a `!` line for each crew with changes that aren't committed, commits that aren't in its backup, no backup at all, or a backup cadrei couldn't check.
- **`--dry-run`** prints the plan and `Nothing was deleted. To go ahead, run cadrei uninstall --all in a terminal and type delete everything.`
- **The typed yes.** In a terminal it asks `This can't be undone. Type delete everything to go on, or press Enter to stop:`. Anything else stops it: `Nothing was deleted.`, exit 1. `--yes` is never enough: `--yes isn't enough to delete every crew.` Without a terminal it refuses (`Deleting everything needs your typed yes, and this isn't a terminal. Nothing was deleted.`) unless `--confirm "delete everything"` is given, with exactly that phrase. That's how the orchestrator runs it, after the user's typed yes in the chat (5.7).
- **With `--archive`, in either order,** it refuses: `--all and --archive don't go together: --archive packs your crews away to bring back later, and --all deletes them.` with `Pick one: cadrei uninstall --archive or cadrei uninstall --all.`
- **Stopping first.** It stops every member with the same teardown as `cadrei uninstall`, the command's own session last. If a team won't stop, or tmux can't list the sessions, nothing is deleted. An orchestrator open in another terminal is named in the plan (the dry run too) and stops a real run before anything changes. The orchestrator this command runs under (by process, not by its variables) is the user's to close afterwards.
- **What it says at the end** is what happened: `Deleted <crews>, cadrei's settings and your archives` names only what went, and when anything couldn't be deleted the last line is `Uninstalled, but not all of cadrei could be deleted: see above.`, exit 2.
- Members can't run it, nor `uninstall`, `uninstall --archive` or `restore`, through three layers (decided in fix rounds 7 and 8): the deny rules `Bash(cadrei uninstall:*)` and `Bash(cadrei restore:*)` in their settings; a PreToolUse hook on Bash in their settings only, `cadrei hook guard`, that refuses (exit 2, the reason on stderr) any command that may run cadrei's uninstall or restore through `env`, a shell, any path, quotes or an expansion, and anything it can't read, and that fails closed when the program is gone; and the commands themselves, by the member's variables (set counts, even empty) and by its tmux window's own `@cadrei_member` mark, found from the process up on every tmux server a crew's sessions were started on. The window mark can't see a command started outside the member's process tree (a `tmux new-window`, a double fork); the first two layers stand there.
- **Which tmux servers:** `up` and the orchestrator's tmux start record their server's socket path in the crew's `.claude/local/state.json` (`tmux_servers`). The teardown and the member check look at the server the environment names, every recorded one, and the default ones (`/tmp/tmux-<uid>/default` and `cadrei-dev`), whatever `CADREI_TMUX_SOCKET` and `TMUX_TMPDIR` say. A team of these crews on any server but the command's own, or a server that can't be listed, stops every uninstall before it changes anything.

#### 7.8.8 Removing the program (decided: added in 0.2.1)

Every uninstall (plain, `--archive`, `--all`) removes a Homebrew install of the program as its plan's last step, so the user doesn't need a second command, and the one yes covers it: the y/N for plain and `--archive`, the typed phrase for `--all`. There's no second question, so the orchestrator runs it with the plan the user approved and needs no flag of its own.

- **Which install:** Homebrew is told from the real path of the running binary, links resolved: `<prefix>/Cellar/cadrei/<version>/bin/cadrei`. cadrei then runs `<prefix>/bin/brew uninstall cadrei` (or `brew` from `PATH` when that one isn't there), with `HOMEBREW_NO_AUTO_UPDATE=1`.
- **The plan:** its last line is `remove the cadrei program (brew uninstall cadrei)`. The dry run shows it, and has no `Then:` line.
- **`--keep-program`** leaves the program, and the run ends with `To finish: brew uninstall cadrei` as before.
- **Order:** brew runs only after all of cadrei's own cleanup, and before the command's own tmux session stops. If brew fails, cadrei says `Couldn't remove the cadrei program: brew says <its first line>. Everything else is done.` and `Run brew uninstall cadrei yourself.`, and exits 2. Nothing of cadrei's cleanup is left half done.
- **Any other install** keeps the printed `To finish: rm <program>` (or, for a build from source, `delete the cadrei you built`). cadrei doesn't delete that file itself: install.sh may have put it in a folder other programs share, or one that needs `sudo`, and an `rm` can't be undone the way `brew install` undoes `brew uninstall`.
- After `--archive`, the start-over line is `brew install rafi-ramdhani/cadrei/cadrei` (the program is gone already).
- Members can't run any uninstall (7.8.7).

### 7.9 Engine and volume

Cadrei follows Docker's idea: the engine is replaceable, and your crew is the volume. (Older docs and the folder layout call a crew "a cadrei".)

| Docker | Cadrei |
|---|---|
| engine | the `cadrei` program, `~/.cadrei/framework` and `~/.cadrei/config` |
| image recipe | a member file, `members/<team>/<role>.md` |
| container (disposable) | a running member session |
| volume | the crew folder, `~/.cadrei/<name>` |
| bind mounts | where each project lives on this machine, kept with the crew, not the engine |

#### 7.9.1 Everything about a crew lives in it

| What | Today | Now | In git |
|---|---|---|---|
| Teams, members, playbook, projects list, grants | the crew | unchanged | yes |
| The tmux choice | `~/.cadrei/config/orchestrator` (decision 10) | `ORCHESTRATOR` in `cadrei.conf` | yes |
| A one-machine tmux override | (none) | `ORCHESTRATOR` in `.claude/local/cadrei.conf` | no |
| Where each project lives on this machine (the places map) | `~/.cadrei/config/places/<cadrei>.json` | `.claude/local/places.json` | no |
| The orchestrator's conversation id (cadrei's check that a resume record is its own) | `~/.cadrei/config/state.json` | `.claude/local/state.json` | no |
| Prompts, settings copies, session records, member states, locks | `.claude/build/` | unchanged | no |

- `.claude/local/` sits under `.claude/`, so members are already denied editing it (`Edit(//**/.claude/**)` in the fixed denies, with its physical path). A member can't point a project at another folder or fake a resume record.
- The template's `.gitignore` gets `/.claude/local/` beside `/.claude/build/`. Existing crews get the line on their first 0.2.1 run (7.9.5).
- The pre-push check never sees these files, since git ignores them. If one was ever committed by hand, the check refuses the push: `! .claude/local/places.json is this machine's own file. Remove it from git (git rm --cached), then push again.`
- `places.json` and `state.json` hold `"version": 1`. Cadrei keeps any keys it doesn't know when it writes them, so an older and a newer cadrei can share a folder.

#### 7.9.2 What's left in `~/.cadrei/config`

Only machine-level things that cadrei can rebuild or ask again:

| Item | If it's gone |
|---|---|
| the default crew | rebuilt: the only crew, or asked once on the 3.11 plan (`d`) |
| the projects folder | rebuilt from the places maps when most projects share a parent folder, else asked the next time a clone needs it (as today) |
| the permissions fingerprint (`member-settings.sha256`) | rebuilt from each crew's committed `member-settings.json` (`git show HEAD:`). A working copy that differs from the commit gets today's "changed outside cadrei allow" warning. |
| health check caches (checked version, last findings) | rebuilt: the next run does the full check |
| consents and their "no" answers (`hook_offer`, kept skill link, kept hook, kept old links) | asked again when it matters |
| one-time markers (`identity_warned`, `team-line-hint`, `first_task_pending`) | shown once more, or not needed (a machine with crews isn't on its first run) |

`~/.cadrei/framework` is rewritten from the program on every run, as today.

Deleting `~/.cadrei/config`, `~/.cadrei/framework` or both at any time loses nothing. The next `cadrei` shows the 3.11 plan and asks only for the machine consents: the skill link in the plan, and the every-chat hook later.

#### 7.9.3 Unplug and plug back in

- **Unplug** is `cadrei uninstall`, with no new command. It already removes only engine parts (the skill link, the every-chat hook, each crew's pre-push check, `~/.cadrei/config` and `~/.cadrei/framework`) and keeps every crew. With places and the resume id now inside each crew, it keeps everything a reinstall needs.
- Its last lines become:

```text
✓ Uninstalled. Your crews and projects are still here.
  Your crews in ~/.cadrei are your setup, so keep them. Reinstall and run
  cadrei to plug them back in.
✓ Removed the cadrei program (brew uninstall cadrei)
```

  With `--keep-program`, or for any install but Homebrew, the last line is `To finish: <the command that removes the program>` instead (7.8.8).

- **Plug back in** is the 3.11 plan.
- **Try it as a brand-new user** stays `cadrei uninstall --archive` (7.8), the only command that moves crews.

#### 7.9.4 Unknown things in a crew

There's no separate version number for a crew. Instead the program skips what it doesn't recognize:

- Unknown `cadrei.conf` keys are ignored, with no warning when opening. `cadrei --check` lists them once: `! cadrei.conf has keys this crew doesn't use: FOO, BAR. They're kept as they are.` Lines that aren't `KEY=VALUE` are handled the same way.
- Unknown files and folders in a crew (from a newer version, or the user's own) are left alone. They're never read, moved or deleted, except by `--archive`, which moves the whole folder.
- Unknown keys in `places.json`, `state.json` and `projects.yaml` entries are kept on write.
- A member file with front matter or sections the program doesn't know still loads as text.
- The fixed denies and health checks still apply to the files they name, whatever version wrote them.

#### 7.9.5 Moving 0.2.0 users over

On the first 0.2.1 run, for each crew on this machine:

1. Move `~/.cadrei/config/places/<cadrei>.json` to `<cadrei>/.claude/local/places.json`.
2. Move the orchestrator's id from `~/.cadrei/config/state.json` to `<cadrei>/.claude/local/state.json`.
3. Add `/.claude/local/` to the crew's `.gitignore` if missing, and commit it (`Keep this machine's notes out of git`). With no git identity, the line is added but not committed, and the 3.6 warning covers it.
4. Remove the moved entries from `~/.cadrei/config` once each move is checked.

It shows one line per crew, once, in the opening screen:

```text
  ✓ main now keeps track of where its projects are on this machine.
```

- It can be run again safely: a step that's already done is skipped.
- When both the old and the new file exist (a run that stopped halfway), the new one wins and the old one is removed.
- A crew linked on two machines: each machine moves its own places file into its own git-ignored `.claude/local/` on its first 0.2.1 run, and nothing about places goes through git. The `.gitignore` commit is made on whichever machine runs first. The other machine gets it with its next pull, or makes the same one-line change itself, which git merges cleanly.

### 7.10 Placeholder secrets

Claude's safeguards have stopped members by mistake. The known case was a member writing a realistic-looking fake GitHub token to test the pre-push credential check. A stopped member goes quiet (7.7), so the cheapest fix is to never write such a string at all.

The framework's shared member protocol (`protocol.md` at the repo root, which every member's prompt includes) gets a new section after "Boundaries", word for word:

```text
## Secrets

- Never write a real-looking secret (an API key, token, password or private
  key) in code, tests, docs or messages, not even a fake one. Use a plain
  placeholder such as `TEST_TOKEN_PLACEHOLDER` or `<your-token>`.
- When a test truly needs something shaped like a real secret, such as a
  test of a secret scanner, build it while the test runs from harmless
  pieces (for example a prefix joined to a repeated letter), so the whole
  string never appears in a file. Add a comment that says why.
- If a task seems to need a real-looking secret written out, stop and ask
  the orchestrator instead.
```

- The same rule goes in the skill's Rules for the orchestrator: `Never write a real-looking secret in a task, a message or a file, not even a fake one. Use a placeholder, and pass this rule on when a task touches secrets.`
- `protocol.md`'s first line follows the naming note: `You are one member of a crew.` (it says "a cadrei" today), and `Do not message other cadrei members` becomes `Do not message other members of your crew`.
- A crew's own `protocol.md` (its additions) can't turn the rule off: the framework protocol comes first, and the skill's rule stands either way.

**The Cadrei repo itself (engineer task T-S1).** A scan of the worktree for the shapes the pre-push check looks for (`internal/backup/backup.go`, the patterns at lines 122 to 128) found four literal secret-shaped strings. Convert each to a value built at run time, with a comment, the way `backup_test.go` already builds its GitHub and AWS cases (`"ghp_" + strings.Repeat("a", 36)`, `"AKIA" + strings.Repeat("X", 16)`):

| File and line | What it is | Built at run time from |
|---|---|---|
| `tests/smoke.sh:347` | an Anthropic-key-shaped value (`sk-ant-` prefix, 39 characters in all) in a test `.env` | `"sk-ant-" + "api03-" + a repeated letter`, joined in the shell (`printf 'ANTHROPIC_API_KEY=%s%s\n' "sk-ant-" "$(printf 'a%.0s' $(seq 32))"`) |
| `tests/smoke.sh:782` | the same shape, in the archive test's `creds.env` | the same helper, defined once near the top of `smoke.sh` |
| `internal/backup/backup_test.go:80` | an Anthropic-key-shaped value (33 characters) in a committed note | `"sk-ant-" + "api03-" + strings.Repeat("a", 20)` |
| `internal/backup/backup_test.go:89` | a private key header line (`-----BEGIN ... PRIVATE KEY-----`) | `"-----BEGIN " + "OPENSSH PRIVATE" + " KEY-----"` |

Nothing else in the repo matched: no other token prefixes with a full-length tail, no private key blocks, and no JWT-shaped strings. The pattern definitions in `backup.go` are prefixes with length rules, not secrets, and stay as they are.

### 7.11 Model and effort per member

Claude Code takes `--model <alias or full name>` (an alias such as `opus`, `sonnet` or `fable`, or a full name such as `claude-sonnet-5-5`) and `--effort <level>` (`low`, `medium`, `high`, `xhigh` or `max`) when it starts. Today cadrei passes neither, so every member gets the user's Claude Code defaults.

#### 7.11.1 Where they're set

A member file can start with front matter:

```text
---
model: sonnet
effort: high
---
# Member: Writer (research team)

You are the writer. ...
```

- Front matter is read only when the file's very first line is `---` and a closing `---` comes within its first 20 lines.
- Only `model` and `effort` are used. Other keys are ignored and kept, as 7.9.4 says. Values may be quoted (`model: "claude-sonnet-5-5"`), and `#` starts a comment.
- The front matter is removed before the file becomes the member's prompt. The prompt starts at the first non-blank line after the closing `---`.
- A file with no front matter works as today.

For the whole crew, in `cadrei.conf`:

```text
MODEL=sonnet
EFFORT=medium
```

- `.claude/local/cadrei.conf` (git-ignored, 4.6) may set `MODEL` and `EFFORT` too, for this machine only.

For one start only:

```text
cadrei up <team>/<role> [project] --model <model> --effort <level>
```

- Either flag can be given alone.
- With a whole team (`cadrei up dev my-app --model sonnet`), it applies to every member that command starts.
- It's not saved anywhere, so the next start goes back to the file and the crew's values.

What wins, first to last:

1. `--model` or `--effort` on this `cadrei up`
2. the member file's front matter
3. `.claude/local/cadrei.conf`
4. `cadrei.conf`
5. nothing: cadrei passes no flag, and Claude Code uses its own default

Model and effort are worked out separately. A file can set only `effort`, and the crew's `MODEL` still applies.

#### 7.11.2 Starting and resuming

- `cadrei up` passes `--model` and `--effort` on every start, a resume included (`--resume <id> --model <m> --effort <e>`). Whether Claude Code honors them on a resume is T-M1. If it doesn't, cadrei still passes them, and the 7.11.4 rows show what was asked for, marked `(from its next fresh chat)`.
- Cadrei records the model and effort each start used in the member's session record (`<build>/sessions/<name>.json`, fields `model` and `effort`). When a resumed member's values differ from its last start, `up` says so:

```text
✓ Started the writer on blog (picked up its chat, now on sonnet, high effort)
```

- A running member keeps what it started with. A changed file reaches it at its next start. The orchestrator offers a restart (stop, then `up`), and the chat resumes.
- An override on a member that's already running does nothing new: `The writer is already running on opus. Stop it first to start it on sonnet: cadrei stop research/writer.`

#### 7.11.3 Checks

Checked before anything starts, by `cadrei up` and by `cadrei --check` (for every member file and the crew's settings):

- **Effort not in the list** (case-insensitive, stored lowercase):

```text
✗ The writer's effort "hgih" isn't one Claude Code knows.
  Use low, medium, high, xhigh or max, in members/research/writer.md.
```

  For the crew setting it says `EFFORT in cadrei.conf`, and for a flag it says `with --effort`.

- **A malformed model**: empty, longer than 200 characters, starting with `-`, or holding a space, a quote, a backslash, a control character or `;|&$<>` and the like. Allowed: letters, digits and `. _ - : / @ [ ]` (so `us.anthropic.claude-...:0` and `opus[1m]` pass).

```text
✗ The writer's model "son net" isn't a model name.
  Use an alias such as opus, sonnet or fable, or a full name such as
  claude-sonnet-5-5, in members/research/writer.md.
```

- **A well-formed model that Claude Code doesn't know** (`model: sonet`) isn't checked by cadrei. It's passed on, and Claude Code's own answer is shown:
  - If Claude Code exits at once, `up` keeps the dead window long enough to read its last lines (`remain-on-exit` on that window, then capture and kill it, T-M2) and prints `The writer didn't start: <Claude Code's last line>.` (16 in the build report's voice) with `Check model: in members/research/writer.md.` under it.
  - If the error only comes with the first message (an API error), the member ends its turn with `StopFailure`, and `ls` shows `idle since <time> · its last turn hit an error` (7.3), with the model shown on its row (7.11.4).

Values are always passed to Claude Code as separate arguments, never through a shell. Members can't change them: `members/**`, `cadrei.conf` and `.claude/**` are already in the fixed denies.

#### 7.11.4 Where it shows

`cadrei ls` shows a member's model and effort only when cadrei passed them (so not Claude Code's own defaults), as a dim note after the state:

```text
main  ~/.cadrei/main

Orchestrator  open in tmux since 14:02 · reopen with cadrei
Team default  sonnet, medium effort
Teams
  research on blog                                 cadrei attach research blog
    * scout      working for 4m
    o writer     idle since 13:40 · opus, high effort
    * editor     working for 1m · opus (this start only)
```

- `Team default` shows only when `MODEL` or `EFFORT` is set for the crew. Then a member row adds a note only where it differs from that default.
- A one-time override says `(this start only)`. A value that will only take effect from the member's next fresh chat (T-M1) says `(from its next fresh chat)`.
- Plain mode uses the same words.
- Under 60 columns, the note moves to its own line under the state, like the safeguard hint.
- `cadrei ls --json`: each running member gets `"model"`, `"effort"` (the values cadrei passed, or absent) and `"model_from"`, `"effort_from"` (`start`, `member`, `machine` or `crew`), and the crew gets `"model"` and `"effort"`. These are added fields, so `version` stays 1.
- The team line (5.8) and the snapshot's `Members` field don't show it. The snapshot gets one line, `- Team default: sonnet, medium effort`, only when one is set.

#### 7.11.5 The orchestrator

The orchestrator does not take `MODEL` and `EFFORT`. Why:

- They're the team's defaults, and a crew may set a cheaper model for its workers.
- The orchestrator holds the consent and permission rules, so it should stay on the model the user picks for their own chat.
- That chat is the user's own, and they can switch it at any time with `/model`.

Optional keys `ORCHESTRATOR_MODEL=` and `ORCHESTRATOR_EFFORT=` in `cadrei.conf` (or the local override) set it on purpose, with the same checks. They're passed on the orchestrator's launch, a resume included. With neither set, the orchestrator gets Claude Code's defaults, as today.

#### 7.11.6 What the orchestrator does when asked

The skill gets a section "Model and effort":

- **A lasting change for one member** ("use Sonnet for the writer"): add or change `model: sonnet` in the front matter of `members/<team>/<role>.md`, commit it (`Use sonnet for the writer`), and say `Done. The writer uses sonnet from its next start.` If the writer is running, offer `Want me to restart it now? It picks up its chat.`
- **One start** ("start the researcher on Sonnet", "just this time"): run `cadrei up <team>/<role> [project] --model sonnet` and say `Started the researcher on sonnet, for this start only.`
- **Unclear which**: ask with one `AskUserQuestion`: `Always` or `Just this time`.
- **The whole crew** ("use Sonnet for everyone"): set `MODEL=sonnet` in `cadrei.conf`, commit, and name any member files that set their own model and so keep it.
- **Effort**: the same, with `effort:`, `EFFORT=` and `--effort`. Map plain words: "think harder" to the next level up, "quick" to `low`.
- **Never** change `ORCHESTRATOR_MODEL` or `ORCHESTRATOR_EFFORT` unless the user asks about the orchestrator itself, and never because a member asked.
- **When `cadrei up` reports a 7.11.3 error**: show it, and offer the fix it names.

#### 7.11.7 Help and docs

### 7.12 The mascot

The brand's lead mascot (the orchestrator, with the headset, in its happy face) is a tiny pixel figure for the terminal, like Claude Code's own startup header: about 12 columns by 3 rows of Unicode half blocks. Each cell is one `▀` (U+2580) with a truecolor foreground (the top pixel) and background (the bottom pixel), or one `▄` (U+2584) the other way round, so 12 by 6 pixels. `▄` is for cells whose top pixel is the terminal's own background (the rounded top corners), drawn with no background color. The brand member is drawing it, in a truecolor version and a 256-color version. There's no ASCII version.

The art is the brand's approved Sturdy glyph (`mascot/lead.pixels`): a green headset band and ear cups around a clay monitor, a dark screen with ivory eyes and smile, the green status bar along the screen's bottom, and two legs. Its palette is all brand colors: green `#3D9F60` (256:71), clay `#C2603E` (256:173), screen `#2A2522` (256:235) and ivory `#FAF8F4` (256:255). `go generate` makes `mascot/truecolor.txt` and `mascot/256.txt` from it.

It always comes as a compact header: the figure, two spaces, and three short lines beside it, one per row.

- **Color tiers** (2.3.1's detection): truecolor terminals get the truecolor figure, and 256-color terminals get the 256-color figure. With 16 colors or fewer, in plain mode, under NO_COLOR, or with `TERM=dumb`, there's no figure: the three lines stay, at the 2-space margin.
- **Fit:** the figure shows only when 2 + its width + 2 + the longest of the three lines fits the terminal's width. Otherwise the lines stay without it, and a line too long for W wraps (2.4). Height is no longer a concern: the header is 3 rows, with or without the figure.
- **Safe inside tmux:** it's only text and color codes, with no image protocol (no kitty graphics, no sixel), so it draws the same inside cadrei's tmux sessions. When the outer terminal lacks truecolor, tmux maps the colors to its nearest 256.
- **Width:** every figure line is exactly the figure's width in columns, padded with spaces carrying the right background. Cadrei counts `▀` and `▄` as one column each (T-B1).
- **Styles of the lines:** on the first line, `cadrei` is bold and the version after it is dim (`cadrei` bold, ` v0.2.1` dim). The other two lines are dim.

Where it shows:

- **The top of every first-run screen** (7.12.1).
- **`cadrei --version` in a terminal** (7.12.2).
- **Nowhere else.** Not on the success screen (one mascot per run is enough, and that screen lasts about half a second before tmux takes it). Not when plain `cadrei` reattaches (tmux takes the screen at once, so nobody would see it). Not when the orchestrator opens in the plain terminal on a later run (Claude Code's own header follows right under it, and two headers stacked look cluttered). Not in `cadrei ls` (run often, and its first line already names the crew). Not in `cadrei help`.
- **README and guide.md:** the image the brand team renders, not the terminal figure.
- **License:** the figure is brand art, like the logo and the characters: Copyright (c) 2026 Rafi Ramdhani Azis (the holder `LICENSE` names), all rights reserved, not covered by the MIT license. `NOTICE` lists its files (`mascot/lead.pixels`, `mascot/truecolor.txt`, `mascot/256.txt`, and any logo or character art under `docs/`), and the README's license line says so. `LICENSE` stays plain MIT, so GitHub still reads it, and release archives carry `NOTICE` beside it. The code that draws and generates the figure (`internal/mascot`, `mascot/gen`) is MIT, like the rest of the code.

### 7.13 For tool builders (decision 17)

People will build things on top of cadrei: a web page that draws a crew, a menu bar light that turns orange when a member waits on the user, a script that pings a phone. Cadrei makes that easy with two read-only outputs and a written promise, and nothing more:

- `cadrei ls --json`, a public, versioned interface (7.13.1);
- `cadrei ls --json --watch`, the same state as a live stream (7.13.2 to 7.13.4);
- a new docs page, `docs/tools.md`, linked from the README and guide.md (7.13.6).

There's no built-in web server (7.13.5).

#### 7.13.1 The contract: `cadrei ls --json`, version 1

The JSON that `cadrei ls --json` prints is a public interface. Its fields are listed in the tables of 7.13.6, and those tables are part of this spec: the build must match them field for field.

Only this JSON and the `--watch` stream are the contract. The screens people read, the text in `problems` and `from`, every other command's output and exit codes, and the files under a crew's `.claude/build/` can change in any release.

Shape rules:

- One JSON object, in UTF-8. `ls --json` indents it with 2 spaces, but whitespace isn't part of the contract.
- Times are RFC 3339 strings, possibly with fractional seconds, in the machine's local offset, as Go writes a `time.Time`: `"2026-10-10T14:02:07.118+07:00"`.
- An optional field is left out when it doesn't apply. It's never `null`. A list with nothing in it is `[]`, never left out.
- Paths are absolute, as the machine has them, with no `~`.
- Field names keep the old word for a crew (`cadrei`, `other_cadreis`, `cadreis`), as the naming note in section 1 says.
- It never holds chat text: no prompts, replies, tool inputs, question text or file contents. That holds for every version, not just 1.
- `cadrei ls --json` never asks a question. When the folder's project is in several crews, it fails with the same message it gives without a terminal, even in a terminal (T-W7).
- Exit codes: `0` with the JSON on stdout. `1` when there's no crew to show, with the message on stderr and nothing on stdout.

Two fields are new in this change, so that everything the 7.3 screen shows is in the JSON. They're added fields, so `version` stays 1:

- `no_activity_since` on a working or waiting member: the time its transcript last changed, present only while the 7.3 `no activity` note shows (10 minutes or more).
- `turn_error: true` on an idle member whose last turn ended in an error (`StopFailure`, 7.3's `its last turn hit an error`).

#### 7.13.2 The compatibility promise

- Within version 1, cadrei only adds: new fields anywhere, new line types in the stream, and new values in a field's list of values (decided before 0.2.1 shipped, forward-compatibility audit M1: member `state`, `waiting_for`, snapshot `reason`, project `state`, `model_from` and `effort_from`, `hook`, `mode`, `orchestrator_opens_in`). It never removes a field, renames it, changes its type, or changes what an existing value means.
- Readers treat a value they don't know as the closest safe one: an unknown member `state` as `unknown`, an unknown `waiting_for` as a plain `waiting`, an unknown snapshot `reason` as `periodic`, an unknown project `state` as `missing`, an unknown `*_from` as not set.
- Only a removal, a rename, a new type or a new meaning bumps `version`, in `ls --json` and in the stream's snapshots at the same time. `ls --json` takes `--json-version 1` now, so tools can pin it; a later cadrei that prints version 2 keeps printing version 1 by default for at least a year, and for `--json-version 1` as long as it can. Any other number is refused (exit 1, nothing on stdout).
- `session` and a member's `name` are keys, never to be split on `-`; `legacy` and `cloned` stay in version 1 (always `false`, and `[]` for the `legacy` list, once cadrei no longer knows 0.1.x). `cadrei`, `cadreis` and `other_cadreis` keep their names for all of version 1.
- Only `ls --json` and its stream promise exit codes. Other commands exit 0 when they did what was asked and non-zero otherwise, with no promise about the number.
- CHANGELOG.md names every change to the contract, added fields and values included, under its own `For tool builders` heading.
- Readers are told (7.13.6) to ignore fields and line types they don't know, to treat unknown values as above, and to check `version` and stop with a clear message when it isn't one they know.

#### 7.13.3 The stream: `cadrei ls --json --watch`

`cadrei ls --json --watch` keeps running and writes one JSON object per line (NDJSON). Each line is compact, with no line break inside it, ends with `\n`, and goes out in one write call, so a reader never sees half a line. It's for programs: it prints the same in a terminal as in a pipe, never uses color, never asks, and doesn't read stdin. `--all` works with it, for every crew on the machine.

It finds its crew once, at start, as `cadrei ls --json` does, and then follows that crew's path for as long as it runs.

Every line has:

| Field | Type | Meaning |
|---|---|---|
| `type` | string | `snapshot`, `heartbeat`, `orchestrator`, `team_started`, `team_stopped`, `member_started`, `member_stopped`, `member_state` or `project_state` |
| `seq` | number | `1` on the first line, then one more on each line |
| `at` | time | When cadrei noticed the change (a member's `since` says when it happened) |

Lines about a crew also have `crew`, the crew's name. Lines about a team or a member also have `session`, `team`, and `project` when the team works on one, as in a `running` entry. `project` is always a project's name, a string, on every line type.

| Type | When | What else it has |
|---|---|---|
| `snapshot` | The first line, every 5 minutes, and whenever small changes can't describe what happened (the reasons below) | `reason`, and `status`: exactly what `cadrei ls --json` (or `--all`) would print at `at` |
| `heartbeat` | After 15 seconds with no other line | nothing more |
| `orchestrator` | The orchestrator opened or closed, or moved between the terminal and tmux | `orchestrator`, the whole object |
| `team_started` | A team instance started (a new tmux session) | `members`, the whole list, as in `running` |
| `team_stopped` | A team instance's tmux session is gone | nothing more, and no `member_stopped` lines before it |
| `member_started` | A member joined an instance that was already running (`cadrei up dev/reviewer my-app` while dev runs) | `member`, the whole object |
| `member_stopped` | A member's window is gone while its instance keeps running | `member`, with `name` and `role` only |
| `member_state` | Any field of a running member's object changed: `state`, `since`, `waiting_for`, `no_activity_since`, `turn_error`, or its model and effort | `member`, the whole object as it is now |
| `project_state` | A project's `state` or `path` changed (a drive unplugged, a folder removed or put back) | `project`, its name, and `project_info`, the whole object |

Snapshot reasons:

| Reason | When |
|---|---|
| `start` | The first line |
| `periodic` | Every 5 minutes |
| `crew_changed` | The crew's own files changed: a member file, a team, a project added or removed, `cadrei.conf` or its local override |
| `crew_gone` | The crew's folder is gone (7.13.4) |
| `crew_back` | The crew's folder is back at the same path |
| `crews_changed` | Only with `--all`: a crew was made, removed, plugged in, or its folder went or came back, or the default crew changed |
| `woke` | The machine slept, or cadrei fell more than 10 seconds behind, so it starts over |

More reasons can come within version 1 (7.13.2); a reader treats one it doesn't know as `periodic`.

An example run (each event is one line; the real lines have no spaces between fields):

**Ordering and merging.**

- The first line is always a `start` snapshot, and `seq` never skips or repeats.
- Cadrei looks in rounds (7.13.4). Within one round the lines come in this order: a snapshot (and then nothing else that round, since it already holds everything), `orchestrator`, `team_stopped`, `member_stopped`, `team_started`, `member_started`, `member_state`, `project_state`. Within one type, they follow the order of `cadrei ls --json`.
- The stream reports where things are, not every hook event. Changes within one round merge: a member that went from working to waiting and back within a second may get no line at all. Every line changes something: a state file rewritten with the same content (7.3 rewrites it on every tool call) gives no line.
- After a reader applies every line up to one, its picture is what `cadrei ls --json` would have printed at that line's `at`. The exceptions are `hook`, `problems`, `other_cadreis` and projects' `found`, which only snapshots bring up to date.
- How fast: a member's state within about 1 second, a team or member starting or stopping within about 2 seconds, a project's folder within about 10 seconds.

#### 7.13.4 When things vanish, stopping, and cost

**When things vanish.**

- A member's window closes: `member_stopped`. Its instance's session ends: one `team_stopped`, with no `member_stopped` before it. `cadrei stop` with no names: one `team_stopped` per instance.
- The tmux server is gone (killed, or it crashed): `team_stopped` for every instance, and `orchestrator` when the orchestrator ran in tmux. The stream keeps running and reports teams again when they start.
- A member's state file goes away (`SessionEnd`) while its window is still there: `member_state` to `unknown`, as `cadrei ls` would show it.
- The crew's folder goes away (deleted, moved, renamed, `cadrei uninstall --archive`, or on a drive that was unplugged): a `crew_gone` snapshot, whose `status` has `cadrei.missing: true`, the orchestrator not running, and empty `running`, `teams`, `projects` and `problems`. After that, only heartbeats, while cadrei checks the path once a second. When a folder is back at the same path, a `crew_back` snapshot. With `--all`, a `crews_changed` snapshot instead, either way.
- An upgrade replaces the `cadrei` program: a stream already running keeps its old code until it's started again. Nothing breaks, since the old code still keeps the version 1 promise.
- The machine sleeps: when it wakes, a `woke` snapshot.

**Stopping.**

- Ctrl-C (SIGINT), SIGTERM and SIGHUP: it finishes the line it's writing, if any, then exits 0 and prints nothing more.
- The reader goes away (the pipe closes, so the next write gets EPIPE or SIGPIPE): it exits 0, with nothing on stderr. When nothing changes, that's at the next heartbeat, at most 15 seconds later (T-W2).
- Any other write error (a full disk, when stdout is a file): `✗ Couldn't write the stream: <error>.` on stderr, exit 1.
- No crew to follow at start: as `cadrei ls --json`, exit 1, the message on stderr, nothing on stdout.
- A panic: it recovers, prints `✗ cadrei ls --watch hit a problem and stopped.` on stderr, and exits 1.
- `--watch` without `--json`, exit 1:

```text
✗ --watch only works with --json. It's for programs that read cadrei's state.
  To look now, run cadrei ls.
```

- It never puts itself in the background and never starts again on its own. It runs for as long as whoever started it keeps it.

**What it reads, and how often.** It reads only what `cadrei ls` reads: the hook state files in `<build>/state/` (7.3), the 7.7 safeguard check with its cache, the orchestrator's lock, the crew's own files, and one tmux call. It never runs `claude`, never uses the network, never reads a pane (`capture-pane`), never sends keys, and writes nothing but the 7.7 cache files that `cadrei ls` writes too.

- **Every second (a round):** a stat of each file in `<build>/state/`, each running member's transcript, the orchestrator's lock, the crew folder, and the crew's own files (`members/` and each team folder in it, `projects.yaml`, `.claude/local/places.json`, `cadrei.conf` and its local override). A state file is read again only when its time or size changed, and the 7.7 tail read runs again only when a transcript changed (the cache). Changes that come from time passing (the 60-second safeguard wait, the 10-minute no-activity note) are worked out from times it already has.
- **Every 2 seconds:** one `tmux list-windows -a` on cadrei's server (with `-S`, T7).
- **Every 10 seconds:** a stat of each project's folder, for `present`, `missing` and `drive`.
- **Every 5 minutes:** the full snapshot, built the way `cadrei ls --json` builds it. It's the only time the stream looks for `found` clones and checks the every-chat hook.
- **Idle cost**, with 10 running members, all idle, over 10 minutes: under 0.5% of one core, no more than 2 wakeups a second, and under 30 MB of memory (T-W1, measured by hand). The tests check the same over 20 seconds (124).

Any number of streams can run at once. They share nothing, and members never wait for them: a member's hooks write their state file and are done.

**The orchestrator doesn't use it.** `cadrei ls --json --watch` never ends, so a Bash call would hang. It isn't one of the orchestrator's pre-allowed commands (5.1), and the skill never mentions it. Members don't use it either.

**Help.** `cadrei help advanced` shows the `ls` line as `cadrei ls [--all] [--json [--watch] [--json-version 1]]`. Plain `cadrei help` doesn't change.

#### 7.13.5 No built-in web server

Cadrei never serves its state over HTTP, a socket or any network port, and there's no `--serve` or `--port` flag. Why:

- A local web server can be reached by any web page open in the user's browser (a page can send requests to `localhost`, and DNS rebinding gets around simple checks), and by every other program on the machine. Doing it safely takes tokens, `Host` and `Origin` checks and careful defaults, kept right in every release.
- Cadrei's state names the user's projects and folders and says what their team is doing. Its members can run commands. A port would be one more way into the program that starts them.
- A wrapper already has what it needs: it runs `cadrei ls --json --watch` as a child of its own program and serves the data the way it likes, with its own security. The stream only reads, so a bug in a wrapper can't start, stop or message anyone through it.

`docs/tools.md` says this in short, with what a wrapper that does serve a browser should do.

````markdown
# For tool builders

Want to show your crew somewhere else? A web page that draws your team, a light in your menu bar that turns on when a member waits for you, a script that pings your phone. Cadrei gives you two ways to read its state, and promises to keep them stable:

- `cadrei ls --json` prints your crew's state once.
- `cadrei ls --json --watch` keeps running and prints a line each time something changes.

Both only read. They never start, stop or message anyone, and they never include chat text: no prompts, replies, questions or file contents.

## Read it once

```sh
cadrei ls --json
```

This prints one JSON object (JSON is a plain-text data format most languages read out of the box). Add `--all` to get every crew on this machine. With `jq`, a small command-line JSON tool, here's who's doing what:

```sh
cadrei ls --json | jq -r '.running[].members[] | "\(.role): \(.state)"'
```

```text
engineer: working
reviewer: waiting
```

It exits with 0 when it worked. When there's no crew to show, it exits with 1, says why on stderr, and prints nothing on stdout; with `--all` it exits with 0 and an empty `cadreis` list instead. It never asks you anything.

## Watch it live

```sh
cadrei ls --json --watch
```

This keeps running and prints one JSON object per line (a format often called NDJSON). The first line is the whole state, the same as `cadrei ls --json`. Every line after it is a change. Here's a small Python script that tells you when someone needs you, both who's already waiting when it starts and who starts waiting later:

```python
import json, subprocess

stream = subprocess.Popen(["cadrei", "ls", "--json", "--watch"],
                          stdout=subprocess.PIPE, text=True)
needs_you = ("waiting", "stopped_by_safeguards")

for line in stream.stdout:
    event = json.loads(line)
    if event["type"] == "snapshot":
        if event["status"]["version"] != 1:
            raise SystemExit("This script knows version 1 of cadrei's JSON.")
        for team in event["status"]["running"]:
            for member in team["members"]:
                if member["state"] in needs_you:
                    print(member["role"], "in", team["team"], "needs you")
    if event["type"] == "member_state":
        member = event["member"]
        if member["state"] in needs_you:
            print(member["role"], "in", event["team"], "needs you")
```

A whole snapshot is one line, so lines can get long. Read whole lines, not fixed-size chunks (in Go, use `bufio.Reader`, or give `bufio.Scanner` a bigger buffer). Keep reading for as long as it runs: if your program stops reading but keeps the stream open, cadrei waits for it, heartbeats included.

Stop it with Ctrl-C, or just close its output. Either way it exits quietly with 0. It reads the same files `cadrei ls` reads and never asks Claude Code anything, so leaving it running costs next to nothing.

### The lines

Every line has `type`, `seq` (1 on the first line, then one more each line) and `at` (when cadrei noticed). Lines about a crew have `crew`, its name. Lines about a team or a member also have `session`, `team`, and `project` when the team works on one. `project` is always a project's name; a `project_state` line has it too, with the whole project in `project_info`.

| `type` | When | Also has |
|---|---|---|
| `snapshot` | First, then every 5 minutes, and when your crew changed in a way the other lines don't cover | `reason` and `status` (the same object as `cadrei ls --json`) |
| `heartbeat` | After 15 quiet seconds | nothing |
| `orchestrator` | Your orchestrator opened or closed | `orchestrator` |
| `team_started` | A team started | `members`, and `legacy`: `true` when it's from cadre 0.1.x |
| `team_stopped` | A team stopped | nothing |
| `member_started` | A member joined a team that was already running | `member` |
| `member_stopped` | A member stopped while its team runs on | `member` (`name` and `role`) |
| `member_state` | Something about a running member changed | `member` (all of it) |
| `project_state` | A project's folder came, went, or is on a drive that isn't connected | `project_info` (all of it) |

A snapshot's `reason` is `start`, `periodic`, `crew_changed` (you added a member, a team or a project, or changed settings), `crew_gone`, `crew_back`, `crews_changed` (only with `--all`) or `woke` (your computer slept). More reasons can come within version 1 (see The promise): treat one you don't know like `periodic`, a whole new picture.

### Keeping your picture right

- Start from the first snapshot, and throw everything away and start again from each new one.
- Apply the other lines in order. Then your picture matches what `cadrei ls --json` would print at that line's `at`. The exceptions are `hook`, `problems`, `other_cadreis` and a project's `found`, which only snapshots bring up to date.
- You get where things are, not every step along the way. Changes within the same second can merge, so a member that went from working to waiting and back may show nothing. A line always means something changed.
- No line for 45 seconds means the stream is gone. Start it again.
- If your crew's folder goes away (moved, deleted, archived, or on a drive you unplugged), you get a `crew_gone` snapshot where `cadrei.missing` is `true` and nothing runs. When it's back, a `crew_back` snapshot.
- `cadrei uninstall --all` deletes every crew: a stream gets `crew_gone` (or, with `--all`, `crews_changed`), and afterwards `cadrei ls --json --all` exits 0 with an empty `cadreis`.

Times look like `2026-10-10T14:02:07.118+07:00` and paths are full paths. A field marked optional is left out when it doesn't apply; it's never `null`. An empty list is `[]`. `cadrei`, `cadreis` and `other_cadreis` mean your crew and your crews: they keep these names for all of version 1.

| `state` | string | What it's doing: `starting`, `working`, `waiting` (on you), `idle`, `unknown` (cadrei can't tell) or `stopped_by_safeguards` (Claude's safeguards stopped its reply, so it won't answer until you look) |
| `since` | time, optional | When it got to that state. Left out for `unknown` |
| `waiting_for` | string, optional | With `waiting` only: `approval` (it wants to run something) or `question` (it asked you something) |
| `no_activity_since` | time, optional | With `working` or `waiting` only: its chat hasn't changed since then, for 10 minutes or more. Maybe someone stopped it with Esc |

| `path` | string | Its folder, or `""` when it's `not here` |
| `cloned` | bool | The same as `state` being `present`. It's kept for older tools |
| `found` | string, optional | When it isn't present: a copy of its repo cadrei found in your projects folder |

`cadrei ls --json --all` has `version`, `orchestrator_opens_in` and `hook` as above, then:

| Field | Type | What it is |
|---|---|---|
| `cadreis` | list | Every crew on this machine, each shaped like the top level above, without `version`, `orchestrator_opens_in`, `hook` and `other_cadreis` |
| `legacy` | list | Teams from cadre 0.1.x, shaped like entries in `running` |
| `unknown` | list | tmux sessions cadrei didn't start, or that belong to a crew it doesn't know anymore, shaped like entries in `running` |

## The promise

- `version` is 1. Within version 1, cadrei only adds things: new fields, new line types in the stream, and new values in the lists of values on this page (a member state, a `waiting_for`, a snapshot reason, a project state, a `model_from` or `effort_from` source, a `hook` setting and the like).
- Version 2 is only for removing or renaming a field, changing its type, or changing what an existing value means.
- Treat a value you don't know as the closest safe one: an unknown member `state` like `unknown`, an unknown `waiting_for` like a plain `waiting`, an unknown snapshot `reason` like `periodic`, an unknown project `state` like `missing`, and an unknown `model_from` or `effort_from` as not set.
- `session` and a member's `name` are keys: compare them whole, and don't split them on `-`. Use `crew`, `team`, `project` and `role` for the parts.
- `legacy` and `cloned` stay in version 1, even once cadrei no longer knows cadre 0.1.x: `legacy` is then always `false`, and the `legacy` list is `[]`.
- Every change to this page, added fields and values included, is in CHANGELOG.md under "For tool builders".
- Your part: ignore fields and line types you don't know, treat values you don't know as above, and check `version`. If it isn't one you know, stop and say so.
- To pin the version you read, pass `--json-version 1` (with `--watch` too). When a version 2 comes, `cadrei ls --json` keeps printing version 1 for at least a year, and `--json-version 1` keeps giving it after that for as long as cadrei can. A version cadrei doesn't print is refused, with exit 1 and nothing on stdout.
- Only `cadrei ls --json` and its stream promise their exit codes (above). Other commands exit 0 when they did what you asked, and something else when they didn't; the exact number can change.
- Only `cadrei ls --json` and its stream are covered. The screens you read, the text in `problems` and `from`, other commands' output, and the files in a crew's `.claude/build/` can change in any release.

## Why there's no web server

Cadrei doesn't open a network port, and it won't. Any web page open in your browser can send requests to a server on your computer, and so can every other program on it. Cadrei's state names your projects and folders, and your team can run commands, so a port would be one more way in, with logins and checks to get right in every release. Your tool already has what it needs: run `cadrei ls --json --watch` from your own program, and show the data however you like.

If your tool serves it to a browser, keep it on your computer: listen on `127.0.0.1` only, check the `Host` and `Origin` headers, and ask for a token.
````

## 9. Technical questions for the engineer

Each one says what to confirm and what to do if the answer is no.

- **T1. Seed prompt (tested).** Works on 2.1.268 and 2.1.295 with `--name`, `--session-id`, `--resume`, `--append-system-prompt-file`, `--settings` and `--allowedTools`. It can't be hidden, so it stays the visible `(cadrei opened this chat)`. The argv must put `--` before it, or `--allowedTools` swallows it (5.1).
- **T2. Prompt file on resume (tested: not re-read).** The snapshot moves to an orchestrator-only `SessionStart` hook passed with `--settings` (5.1). It fires on startup and resume, and shows nothing in the chat. Side note for later: an edited role file doesn't reach a resumed member either.
- **T3. Pre-allowed commands (tested).** The 5.1 rules go in the orchestrator's `Launch` only (`Role == runtime.Orchestrator`), never in `member-settings.json`. Exact rules match only those commands: other flags, `&&`, `;`, a pipe and a redirect all still ask. Reading `playbook.md` and loading a skill don't ask. `cadrei ls --all --json` is added as a seventh rule and `cadrei hook skip` as an eighth, and the skill names the exact forms. An orchestrator started by the every-chat hook can't get CLI flags, so it keeps asking.
- **T4. Member state hooks (tested).** All the events in 7.3 fire from a `--settings` file on 2.1.268 and 2.1.295 with the same payloads. `notification_type` can't tell a question from an approval, so waiting comes from `PermissionRequest` and its `tool_name`. `idle_prompt` is a reminder while idle. The queued-prompt race is handled as 7.3 says.
- **T12. Interrupts and errors (tested).** Esc fires no event, at an approval or during a tool, so 7.3 shows `no activity` from the transcript file's time. An API error fires `StopFailure` (no `Stop`), mapped to idle with its error note. A real usage limit wasn't triggered; its `StopFailure` error value is `rate_limit`.
- **T13. Messages waiting for approval (decided: not tested).** A held message needs a member in the other mode class (bypassPermissions), and testing it means accepting Claude Code's bypass dialog, which the user chose not to do. The fallback stands: such a member shows `idle`, and the orchestrator keeps today's advice (match `PERMISSION_MODE`).
- **T14. Hook cost (tested).** About 4 ms per call (median, like `/bin/sh -c true`). Exit 0 with output shows nothing in the window; exit 1 shows a hook error. The 7.3 rules follow from this: always exit 0, print nothing, `"timeout": 5`, synchronous.
- **T5. Single-key input (tested).** Raw mode with `golang.org/x/term` works, and the terminal comes back after a key, Ctrl-C, SIGTERM and SIGHUP. Build notes: turn raw mode on before printing the prompt (a key typed early is echoed otherwise). Handle the bytes of each read one at a time (`x` then Enter can arrive as `"x\r"`), and treat an escape sequence (an arrow key) as one ignored unit. In raw mode Ctrl-C arrives as byte 0x03, not SIGINT: treat 0x03 and 0x04 (Ctrl-D) as `q`. Fall back to line reads when stdin isn't a terminal or `CADREI_TEST_TTY=1`.
- **T6. Version probes (tested).** All take about 0.01 s (`claude auth status` 0.15 s). Reuse the 15-second limit in `output()`. Parse `tmux -V` forms like `3.8`, `3.5a` and `next-3.x`. Detect a missing git by `git --version` failing, not by looking it up on PATH: on macOS `/usr/bin/git` exists without the Command Line Tools.
- **T7. One tmux server (tested).** Today, without `CADREI_TMUX_SOCKET`, tmux follows `$TMUX`, so inside another server cadrei would start a second orchestrator there and `ls` would look empty. Pin every call with `-S <path>`, compare that path with `$TMUX` before the first comma, and never `switch-client` across servers (3.3).
- **T8. Attach as a child (tested).** Workable. tmux exits 0 both when the user leaves and when the session ends, so check `Has(session)` before printing the line (4.3).
- **T-B1. The half-block glyph (manual).** In Terminal.app, iTerm2, Ghostty and VS Code's terminal, with their default fonts, check that `▀` fills exactly the top half of a cell and `▄` the bottom half, with no gap or overlap between rows, so the art has no stripes. There's no easy way to detect a font that breaks it, so it stays a manual check. Also check with "ambiguous characters are double-width" turned on (iTerm2 and some CJK setups): U+2580 and U+2584 are East Asian ambiguous width, so the art doubles and breaks there. If that matters, add an opt-out (for example `CADREI_ART=0`), but don't guess the font.
