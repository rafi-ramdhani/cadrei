# Onboarding spec (0.2.1, 66f1479): technical questions T1-T14, tested

Tested on macOS 26.6.2, Claude Code 2.1.295 and 2.1.268 (npm `@anthropic-ai/claude-code-darwin-arm64@2.1.268`, run from scratch with DISABLE_AUTOUPDATER=1; the installed `claude` link still points at 2.1.295), tmux 3.8 (installed) and tmux 3.2a (built from source into scratch). Every tmux test used a private `-L cadreit-*` socket; every Claude Code run used `--model haiku`, one-word prompts, `CADREI_OFF=1`, `--setting-sources project,local`, and was ended right away.

Verdict: GO, with the spec changes listed at the end.

## T1. Seed prompt

Works on 2.1.268 and 2.1.295 with `--name`, `--session-id`, `--resume`, `--append-system-prompt-file`, `--settings` and `--allowedTools`.

- New chat: the pane showed `❯ go` then `⏺ ALPHA` (prompt file rule), sent with no key press.
- Resume: `--resume <id> ... -- zap` showed `❯ zap` after the old history, and the model answered it.
- The seed is a normal, visible user message. Neither version has a flag to hide it (`claude --help` has nothing for a hidden or initial prompt).
- Gotcha: `--allowedTools` is variadic and swallows a positional prompt that follows it. `claude -p --allowedTools 'Bash(cadrei ls)' SEEDWORD` gives `Error: Input must be provided either through stdin or as a prompt argument` on both versions. `... --allowedTools 'Bash(cadrei ls)' -- 'Reply with the single word PONG'` gave `PONG` on both.

Spec: Launch must end the argv with `-- "(cadrei opened this chat)"`. Keep the visible text.

## T2. Prompt file on resume

Not re-read, on either version.

- Resumed with a new prompt file whose only rule was `zap` -> `YANKEE-9`, seed `zap`:
  - 2.1.268: "I'm not sure what you'd like me to do with "zap"."
  - 2.1.295: "I don't have an instruction for "zap" in this test."
- Control: a fresh session with a new file (`word` -> `ZULU-7`) answered `ZULU-7`. Resuming the old session with that file instead ran the old file's `date` rule and said `word` "isn't one of the test commands I know (go, run, slow, ask, ok)".
- Side effect today: an edited role file never reaches a resumed member or orchestrator.

A way that works on both versions: a `SessionStart` hook in a `--settings` file that prints the snapshot to stdout.
- On `--resume`, `SessionStart` fires with `"source": "resume"`. A hook printing "If the user message is exactly `zap`, reply XRAY-5" made both versions answer `XRAY-5`.
- The injected text did not show in the chat: the line above `❯ zap` was the old "See ya!".
- It also fires on startup (and on clear and compact).

Spec: deliver `## Right now` through an orchestrator-only `--settings` file with a `SessionStart` hook (for example `cadrei hook snapshot`), and keep the prompt file for static text. The spec's fallback (`cadrei ls --json` after the seed) also works, but costs a tool call before the greeting.

## T3. Pre-allowed commands

Confirmed on both versions. Method: `claude -p --permission-mode default --allowedTools <the six rules>` with a stub `cadrei` on PATH; print mode turns "ask" into a recorded `permission_denials` entry.

- Ran without asking: `cadrei ls`, `cadrei ls --json`, `cadrei ls --all`, `cadrei ls --json --all`, `cadrei allow`, `cadrei allow list`. The stub logged all six.
- Asked (denied):
  - `cadrei ls -x`
  - `cadrei ls && touch <scratch>/pwned-and`
  - `cadrei ls; touch ...`
  - `cadrei ls | touch ...`
  - `cadrei ls --json > file`
  - `cadrei allow add Bash(*)`
  - No marker files were created.
- No prompt: reading `playbook.md` in the working folder, and loading a skill with the Skill tool.
- Bare `cadrei allow` is `runAllowList` (read-only), so it's safe.
- Gap: `cadrei ls --all --json` (other order) isn't covered. Either the skill names the exact forms, or add the two reversed rules.
- Cost: $0.007 on 2.1.295, $0.074 on 2.1.268.

## T4. Member state hooks

All five events, plus `PermissionRequest` and `StopFailure`, fire from a `--settings` file on 2.1.268 and 2.1.295. The payload fields are the same on both.

Timeline (2.1.295; 2.1.268 matched it event for event):

| Moment | Events |
|---|---|
| startup | SessionStart (source startup) |
| prompt | UserPromptSubmit |
| tool | PreToolUse, PostToolUse |
| turn end | Stop |
| approval dialog | PreToolUse, PermissionRequest (at once), Notification `permission_prompt` "Claude needs your permission" (6 s later) |
| AskUserQuestion | PreToolUse(AskUserQuestion), PermissionRequest(AskUserQuestion), Notification `permission_prompt` (6 s later) |
| idle after a turn | Notification `idle_prompt` "Claude is waiting for your input", 58 to 60 s after Stop |
| /exit | SessionEnd (reason prompt_input_exit) |

- `notification_type` can't tell a question from an approval: both are `permission_prompt`. The `tool_name` on `PermissionRequest` or `PreToolUse` can (`AskUserQuestion`).
- `PermissionRequest` arrives 6 s before the Notification, so it's the better "waiting" signal.
- `idle_prompt` is a reminder while idle, not "waiting on you".
- `elicitation_dialog` exists but is for MCP elicitation, not AskUserQuestion.
- Race seen once: when a prompt is queued at the end of a turn, its `UserPromptSubmit` (60032.067) arrived before the previous turn's `Stop` (60032.361). Both carried the previous `prompt_id` (the new id only appears from the next PreToolUse), so `prompt_id` can't sort them out. Cadrei would show idle until the member's next tool call.
- Cross-session messages arrive as `UserPromptSubmit` with a prompt starting `<cross-session-message`.

Spec (7.3 table):
- waiting: `PermissionRequest` (tool `AskUserQuestion` -> "asked you something", else approval)
- idle: `Stop`, `StopFailure`, `SessionStart`, `Notification idle_prompt`
- working: `UserPromptSubmit`, `PreToolUse`, `PostToolUse`
- Treat a `Stop` that arrives within about 1 s of a `UserPromptSubmit` as working, or accept the short glitch.

## T12. Interrupts and errors

- Esc at an approval: no event at all on either version (no Stop, PermissionDenied or PostToolUseFailure). State stays "waiting".
- Esc during a running tool (`perl -e "sleep 25"`, pre-allowed): no event either. State stays "working".
- The transcript gets `[Request interrupted by user for tool use]`, and its path is in every hook payload (`transcript_path`).
- API error (`ANTHROPIC_BASE_URL=http://127.0.0.1:9`, `-p`):
  - Events: SessionStart, UserPromptSubmit, then `StopFailure {"error": "server_error", "last_assistant_message": "API Error: Connection refused ..."}`, then SessionEnd. No `Stop`.
  - The `StopFailure` error values on both versions include `rate_limit`, `billing_error`, `authentication_failed`, `overloaded` and `max_output_tokens`. A real usage limit wasn't triggered.

Spec:
- Add `StopFailure` to the hooks and map it to idle (or "stopped on an error").
- Keep the "no activity for Nm" fallback for both working and waiting, and take "last activity" from the transcript's file time rather than the state file.

## T13. Messages waiting for approval

Not reproduced.

- Messages from a "prompting" sender were delivered at once to `default` and `auto` receivers. The sender's `from-mode` is "prompting" for both `default` and `auto`. Events: `UserPromptSubmit` then `Stop`.
- A held message needs the other mode class, "skipping" (bypassPermissions).
- Starting a `--permission-mode bypassPermissions` session shows a responsibility dialog ("By proceeding, you accept all responsibility...") that is saved in `~/.claude.json`. The test declined it and killed the session; `~/.claude.json` has no bypass keys.

Decided by the user: skip the bypass-mode test, so whether a hook fires for a held message stays unknown. The spec keeps its fallback (idle, and today's `PERMISSION_MODE` advice).

## T14. Hook cost

Go state hook (read the JSON, write a temp file, rename), 200 runs:

| Process | Median | p95 | Max |
|---|---|---|---|
| Go state hook | 4.0 ms | 4.6 ms | 510 ms (one cold start) |
| `cadrei --version` (0.2.0) | 4.3 ms | 4.7 ms | |
| `/bin/sh -c true` | 4.3 ms | 4.8 ms | |

Visibility (2.1.295 transcript):
- Exit 1 with stderr shows in the member's window: `PostToolUse:Bash hook error` / `Failed with non-blocking status code: HOOKFAIL-visible`.
- Exit 0 with output on both stdout and stderr shows nothing (checked on both versions).
- Per-hook `"timeout": 1` cut a 6 s hook to about 1 s (8.3 s total became 2.8 to 3.7 s). `"async": true` didn't block (1.7 to 2.6 s). Both versions honor both.

Spec: the hook always exits 0, prints nothing, recovers from panics, never blocks (no network, no locks), sets `"timeout": 5`, and stays synchronous (async could reorder state writes). Note that exit 2 would block the tool, and stdout from `UserPromptSubmit` or `SessionStart` goes into the model's context.

## T5. Single-key input

Works (x/term v0.46.0, test program under a private tmux).

- `p` was read without Enter.
- The terminal was restored (`stty -g` the same before and after) after a key, Ctrl-C, SIGTERM and SIGHUP. SIGKILL can't be handled.
- Ctrl-C in raw mode arrives as byte 0x03, not SIGINT. Treat 0x03 and 0x04 as `q`.
- From a pipe it falls back to a line read (`line read: "p"`).
- Build notes:
  - One read can hold several bytes: `x` then Enter arrived as `"x\r"` and was ignored as a whole. Handle bytes one at a time, and treat an escape sequence (arrows) as one ignored unit.
  - Turn raw mode on before printing the prompt; a key typed early was echoed by the cooked tty.

## T7. Inside tmux on another server

The spec's premise doesn't hold today.

- Without `CADREI_TMUX_SOCKET`, cadrei runs tmux with no `-L`, and tmux then uses the socket in `$TMUX`. With `TMUX` pointing at server B, `tmux has-session -t =bee:` (no `-L`) found B's session, and `display -p '#{socket_path}'` printed B's socket.
- So inside another server, cadrei creates the orchestrator and teams on that server. Ones already on the default server are invisible: a second orchestrator, and an empty `ls`.
- Same server (`TMUX=A`): `switch-client -t =two:` exited 0 and switched the client.
- Different server (`TMUX=B`, `tmux -L A switch-client -t =one:`): exited 0 and switched a different client attached to A. In real use that's another terminal.
- No client on the target server: `no current client`, exit 1.

Spec:
- Pin every cadrei tmux call to one server (`-S <default socket path>`, or `CADREI_TMUX_SOCKET`).
- Detect "another server" by comparing the part of `$TMUX` before the first comma with that path.
- In that case, open in the current pane (the 3.3 line), and never `switch-client` across servers.

## T8. Attach as a child

Workable. Test: a Go parent ran `tmux attach` as a child with stdio inherited and SIGINT/SIGQUIT/SIGTSTP ignored, inside an outer private tmux.

| Case | tmux output | tmux exit | Parent |
|---|---|---|---|
| prefix d | `[detached (from session one)]` | 0 | printed its line |
| Ctrl-C | goes to the app in the pane; the session died | 0 (`[exited]`) | not signalled |
| session killed | `[exited]` | 0 | printed its line |

The exit code can't tell "you left" from "the orchestrator ended". Spec: after attach returns, print "Your orchestrator is still running..." only if `Has(session)` is still true. Inside tmux, `switch-client` returns at once, so there is no line in that case (as the spec says).

## T9. Trusting a new cadrei

Feasible as specified. Fresh `CLAUDE_CONFIG_DIR`:
- Claude Code created `.claude.json` at its very first launch, before login (`firstStartTime`, `userID`, `migrationVersion` and so on, plus `backups`, `cache` and `sessions`).
- So a first run before Claude Code ever ran finds no file. Today's code returns "Claude Code has not created its config yet", so show the 3.1 `!` line as the spec says.
- A pre-made file holding only `{"projects":{"<dir>":{"hasTrustDialogAccepted":true}}}` came through Claude Code's first start untouched.
- Whether that entry later skips the trust prompt couldn't be checked without a login, so cadrei shouldn't create the file itself.
